Using Cursor during our Flutter Workathon — what I figured out the hard way

At slice’s internal Flutter Workathon — we took real production screens and rebuilt them Flutter-first.

We had just 48 hours to build, test, and submit our screen for review by the panel.

My team wrote ~10,000 lines of code in 2 days, made the screen production-ready, and placed 2nd out of 9 teams.

Highlights:

✅ Had the screen skeleton and base architecture up and running in under 3 hours — a solid head start.

✅ Ported deeply nested iOS logic to Flutter without rewriting every edge case

✅ Let Cursor auto-generate ~80% of our code.

But the real win?

Learning how to use AI when it matters — under time pressure, on complex code, while making decisions fast.

We paired with Cursor AI.

Here’s everything I learned pairing with Cursor through an intense, high-pressure build sprint 👇

If you’re building with AI, these small tips might save you hours of pain (and mistakes I already made for you 😅)

Don’t jump straight to: “Fix this.”#

It’s tempting to say “Fix this” and watch the AI go. That’s how we broke things early.

Now I always start with: “Read the code. Understand the scope. Break it down into steps. Suggest a plan — but don’t touch the code yet.”

This gives me visibility into Cursor’s mental model — and lets me shape it before it acts.

Even for tiny bugs, this has massively improved outcomes.

Move in Phases — and Validate Each Step#

Early on, we got our screen working in a few hours. This velocity was very addictive.

Felt like magic — until a bug from Phase 1 came back to bite us.

This ended up costing us more time than we gained. It completely offset the speed advantage.

The fix: Prompt → Test → Validate → Only then move to next phase

You’re not slowing down. You’re staying in control.

Set Up Your Environment — Once and Right#

I said “use flutter” and it used the wrong global version.

Should’ve said: “Use fvm with Flutter”

Lesson: AI won’t guess your setup. You need to define it.

The smarter way? Set this as a cursor project rule so you don’t have to repeat it in every prompt. One-time setup. Team-wide benefit.

Use Rules to Stay Sane#

Think of rules as guardrails for your prompting system — small up-front effort, compounding payoff.

One rule I rely on:

After making code changes, analyze the full project for compile errors.

It’s caught breakages before runtime after AI change more times than I can count.

Other rules I’ve set (or wish I did earlier):

✅ Always use fvm flutter

✅ For API models: only use fields explicitly provided in the JSON prompt — no guessing, no hallucination

Why? Because you give Cursor a clean JSON, and it still confidently invents 3 extra fields that sound helpful — but don’t exist.

Now I either add a rule or say it upfront in the prompt:

Use only these keys. Do not infer or add anything.

This mindset — of being painfully explicit — has saved hours of debugging later on.

One Task = One Window#

We had one long Cursor thread with 6 context shifts.

It started blending assumptions across steps.

→ Hallucinated past decisions

→ Broke earlier logic

Now, I:

→ Open one window per task

→ Keep prompt history short

→ Scope context tightly

Cleaner conversations. Fewer side effects. Better code

Pick the right model — they’re not interchangeable#

(⚠️ Not an expert. Just sharing what’s worked for me. Try and decide for yourself.)

Different models behave differently — in quality and cost. Some requests = 1x, others = 2x, some = 0.5x.

If you’re not careful, you’ll fly through your quota without even realizing why.

🚫 Turn off Auto Mode + Max Mode — seriously. Max Mode just goes big on context window — super expensive and rarely needed. Learnt it the hard way by exhausting my quota in 2 days.

What I use:

🏆 Claude 4 Sonnet → My default for all coding tasks, excellent for structured refactors, minimal hallucination.

🧠 Claude 4 Sonnet (thinking) → Great for planning, but costs 2x. I use only when needed and I’m not getting the required output from Claude 4 Sonnet.

🧾 GPT-4 (via Cursor) → Nice for writing docs and summaries. I use it for rewriting my prompts in a way that can be understood by AI. For coding? Hit or miss for me — but I’ve seen others have good results, especially for simpler UI logic

⚡ Gemini 2.5 Flash → Fast, cheap, and usually wrong I rarely accept its output — especially when it touches multiple files.

🧠 Gemini 2.5 Pro → Still exploring; possibly useful for large-context thinking.

Choose your AI like you’d choose a teammate:

Some are architects. Some are coders. Few are both.

** There are many more to explore — but I’ll save that for a dedicated deep dive when I get time. In practice, good models usually find you through word of mouth. Trust the devs who’ve broken things with them 😅

Never let AI run your terminal#

I’ve seen Cursor hallucinate command chains, delete important files, and even try a force push. You can use AI to suggest terminal commands. But you run them.

Always.

Don’t lose touch with the code#

AI feels like a productivity steroid — until you realize you don’t understand what just changed.

If a task is small and you know the fix, as counter intuitive as it may sound (or not): write it yourself.

Stay hands-on. You’re not outsourcing thinking — you’re augmenting it.

🎯 This isn’t just about prompts.

It’s about designing reliable workflows that work with AI, not around it.

Shipping is easy. Shipping things that are correct, maintainable, and explainable — that’s hard.

My takeaway:#

AI won’t replace you.
But poor prompting and losing touch with fundamentals might 😅

Treat it like a dev partner — not a magic trick.

If you’re experimenting with AI in your dev workflow — happy to connect, share prompts, or jam on this!
