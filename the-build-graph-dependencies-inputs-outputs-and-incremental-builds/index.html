When your incremental build lies

July 5, 2026 · 5 min · Beyond Swift
📊 ~... unique reads

Here is a Run Script phase that regenerates an API client from a spec file. It works. But every clean-looking incremental build takes four extra seconds, and once a week someone gets a stale client and loses an hour.

# Run Script phase: "Generate API client"
swift run codegen --input api-spec.yaml --output Generated/APIClient.swift

Two questions before we go on. Why does this script run on every build, even when nothing changed? And why, when the spec does change, does the app sometimes compile against the old generated file anyway?

Same root cause. Both answers are about what the build system can and cannot see. By the end you will know the one field that fixes both, and why “Clean Build Folder” is a symptom, not a fix.

The build system only sees declarations#

Xcode’s build system (llbuild) is a task graph. Every task declares its inputs and outputs. Before running a task, the system compares the two: if every output exists and is newer than every input, it skips the task. That skip is the entire value of an incremental build.

The critical word is declared. The system does not watch your filesystem. It does not know your script reads api-spec.yaml. It knows exactly what you told it, and nothing else.

flowchart LR
  In["Declared inputs"] --> Task["Task"]
  Task --> Out["Declared outputs"]
  Task -. "compare mtimes" .-> Skip["Skip if outputs newer"]

So the graph fails in exactly two directions. It reruns work it has no declared output to check freshness against (over-build). And it skips work whose inputs changed but were never declared, so the diff sees nothing new (under-build, the stale one). Our script hits both.

An undeclared script runs every time#

Look at the phase again. It has no output files listed. Xcode even warns you:

Run script build phase 'Generate API client' will be run during every
build because it does not specify any outputs.

That warning is the whole story. With no declared outputs, the system has nothing to compare, so its only safe choice is to run the task every single time. Four seconds, every build, forever.

Worse, that task sits upstream of Compile Sources. Rerunning it rewrites APIClient.swift with a new mtime every build, so that file always recompiles even when its contents did not change. When the regenerated code changes an interface Swift tracks, the recompile cascades to the files that import it. One undeclared script quietly widens into rebuilding more than it should.

The fix is to make the script a real graph node by declaring what it eats and what it produces:

Input Files:
  $(SRCROOT)/api-spec.yaml

Output Files:
  $(SRCROOT)/Generated/APIClient.swift

Now the rule is trivial: run only when api-spec.yaml is newer than APIClient.swift. Change the spec, it regenerates. Touch nothing, the build log marks the phase skipped instead of burning four seconds. For many files, point at an .xcfilelist instead of listing each path.

Undeclared inputs are how it goes stale#

Now the second bug, the expensive one. Suppose the script also pulls in shared fragments:

swift run codegen --input api-spec.yaml --include shared/*.yaml --output Generated/APIClient.swift

You declared api-spec.yaml as the input. You did not declare shared/*.yaml. So when a teammate edits shared/money.yaml, the input the system watches (api-spec.yaml) is untouched, the output still exists and looks newer, and the task is skipped. The build is green. The generated client is stale. The app compiles and ships against yesterday’s contract.

This is the real reason teams develop a “just clean it” reflex. Clean Build Folder deletes every output, which forces every task to run because its outputs are now missing. It works because it makes the graph correct by making it empty. That is treating a lie in the graph by throwing the graph away.

The actual fix is to declare the real inputs, all of them:

Input Files:
  $(SRCROOT)/api-spec.yaml
  $(SRCROOT)/shared/money.yaml
  $(SRCROOT)/shared/user.yaml

If your inputs are a moving glob, generate an .xcfilelist as part of the build and feed that. The principle does not bend: a task is only as correct as its input list is complete.

Swift compilation is its own graph#

The same skip-if-unchanged logic runs one level down, inside a single module, and it has a mode switch worth knowing.

SWIFT_COMPILATION_MODE = singlefile (the Debug default, shown as “Incremental” in Xcode’s Build Settings dropdown) compiles file by file and tracks cross-file dependencies, so changing one file recompiles it and the files that depend on its declarations. Fast for a one-line edit.

SWIFT_COMPILATION_MODE = wholemodule (the Release default) compiles the whole module as one unit. Any change recompiles everything in the module, but the optimizer sees across every file, which is why release builds use it.

The lever that matters day to day: if incremental mode is recompiling far more than the file you touched, the usual cause is a widely imported file. A change to a type that half the module imports invalidates half the module. That is the graph being correct, not broken. The fix is smaller modules or narrower imports, not a build setting.

Read the graph, do not clean it#

When a build behaves oddly, the instinct to reach for Clean Build Folder is the instinct to stop debugging. Two moves recover the real answer.

Open the build log in the Report navigator and read why a task ran. The log tells you the input it considered newer. If a task you expected to skip ran anyway, its input list is wrong. If a task you expected to run was skipped, its input list is incomplete, and that is your stale bug.

And check the mtime directly when you suspect staleness:

ls -la Generated/APIClient.swift api-spec.yaml shared/*.yaml
# is any input newer than the output the build swore was fresh?

A clean build hides the bug for one build and it comes back. A correct input list makes it impossible.

The build graph does exactly what you declare and nothing you assume. Every stale artifact and every needless rebuild traces back to one gap between the two, and the fix is always to close that gap, never to delete the graph.
