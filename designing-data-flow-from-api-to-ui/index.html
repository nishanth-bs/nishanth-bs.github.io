Data Flow From API to UI: The Parts That Actually Break

September 9, 2025 · 6 min · Beyond Swift

Ask anyone to draw API-to-UI data flow and you get the same picture: networking fetches, a view model holds state, the view renders. Boxes and arrows, two minutes on a whiteboard. The diagram is never where data flow breaks. What breaks is everything the diagram hides.

So start with a real one. Here is a view model method close to what a lot of production code actually contains. It passes review at a glance:

func loadData() {
    if let local = persistence.load() {
        data = local            // show cache
    } else {
        networking.fetch { [weak self] result in
            self?.data = try? result.get()
            self?.persistence.save(...)
        }
    }
}

Read it before scrolling. What does a user see the second day they open this screen?

They see stale data forever. If the cache is populated, this code shows it and never touches the network again. There is no path to freshness short of deleting the cache. The diagram was right and the behavior is wrong, which is the whole point: the parts that decide whether data flow holds up are not on the diagram.

Single source of truth#

One layer owns the truth. Everything else feeds it. The failure mode is letting the network response and the cache both count as “the data,” so the UI reflects one on one screen and the other on another, and they drift.

Pick one source the UI reads from, and make everything else feed it. Usually that is the persistence layer or an in-memory store: the network does not update the UI, it updates the store, and the UI observes the store. This sounds like a small distinction and it is the difference between an app where the same item shows two different states on two screens and one where it cannot.

When the store is the only thing the UI reads, two screens showing the same object are showing the same value by construction. You did not have to keep them in sync. They were never separate.

Stale-while-revalidate, not cache-or-network#

Show the cached value now, refresh in the background, update the store when it lands. This is the fix for the opening bug and the right default for most reads. Cache and network are not an either/or: cache is for latency, network is for truth, and you want both at once.

func load() {
    if let cached = store.value { state = .loaded(cached) }   // instant, possibly stale
    Task {
        do {
            let fresh = try await networking.fetch()
            store.update(fresh)                                // truth arrives, UI re-renders
        } catch {
            if store.value == nil { state = .failed("Could not load.") }
            // if we already showed cache, a failed refresh is not a failure the user sees
        }
    }
}

Note the error handling. A failed refresh when you already have cached content is not an error state, it is a no-op the user never notices. Treating every network failure as a full-screen error is its own common bug, and it punishes users on flaky connections who had perfectly good cached data to look at.

Duplicate in-flight requests#

The same fetch fires several times, and the slow one wins. The user taps refresh twice, or two screens observing the same resource both request it on appear. Redundant calls are the small problem. The real one is the race: the slower response lands last and overwrites newer data with older.

The fix is to dedupe at the layer that owns fetching. Keep a handle to the in-flight task per resource and hand the existing one to any caller that asks while it is running.

actor ResourceLoader {
    private var inFlight: [Key: Task<Value, Error>] = [:]

    func load(_ key: Key) async throws -> Value {
        if let existing = inFlight[key] { return try await existing.value }
        let task = Task { try await fetch(key) }
        inFlight[key] = task
        defer { inFlight[key] = nil }
        return try await task.value
    }
}

An actor here is not decoration. Multiple screens calling load concurrently is exactly the data race that actors exist to prevent, and the dictionary of in-flight tasks is shared mutable state that would be unsafe on a plain class.

Threading and the main actor#

State that drives UIKit or SwiftUI must be mutated on the main actor. The easiest way to break this is to write a @Published property from inside a background completion handler:

final class FeedViewModel: ObservableObject {
    @Published var items: [Item] = []

    func load() {
        networking.fetch { result in
            self.items = (try? result.get()) ?? []   // wrong: mutates UI state on the network's thread
        }
    }
}

That callback runs on whatever thread the networking layer finished on, and writing items there mutates SwiftUI-observed state off the main actor. That is a data race, not a style nit: it works on your fast device, janks or corrupts state on a user’s, and Swift 6 strict concurrency rejects it at compile time. Mark the view model @MainActor and let the compiler hold you to it:

@MainActor
final class FeedViewModel: ObservableObject {
    @Published var items: [Item] = []

    func load() async {
        let fresh = (try? await networking.fetch()) ?? []
        items = fresh   // better: @MainActor guarantees this runs on main; the check is at the call site, not here
    }
}

With async/await and a @MainActor view model the hop back to main is automatic and checked. With completion handlers you have to dispatch back by hand, and the day you forget is the bug that does not reproduce on the device sitting on your desk.

Optimistic updates, when latency is the enemy#

Update the store now, send the request, roll back if it fails. For writes where the round trip feels bad (liking, favoriting, reordering), do not make the user wait for the server:

func toggleLike(_ post: Post) {
    let previous = post                                 // keep the exact old value
    store.update(post.id) { $0.isLiked.toggle() }       // update now, UI feels instant
    Task {
        do {
            try await networking.setLike(post.id, liked: !previous.isLiked)
        } catch {
            store.set(post.id, previous)                // rollback: restore the old value exactly
        }
    }
}

That is what makes an app feel instant. It is also where correctness gets genuinely hard, because the UI can now show a state the server never accepted, and the rollback has to put things back exactly, including whatever changed while the request was in flight. Reach for optimistic updates only where the latency actually hurts, because every one is a small distributed-systems problem you are signing up to maintain. Most reads do not need it. A few high-frequency writes do.

The shape that holds up#

Strip away the patterns and the durable version of API-to-UI flow is: one store the UI observes, fed by a fetch layer that dedupes and writes truth into the store, with cache for speed and network for freshness running together rather than as alternatives. The view model coordinates and owns presentation state on the main actor. None of that shows up in the two-minute box diagram, which is exactly why the two-minute diagram is not the answer to the question.
