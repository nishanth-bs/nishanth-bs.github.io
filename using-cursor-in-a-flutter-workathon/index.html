Using Cursor in a Flutter Workathon

July 9, 2025 · 5 min · Beyond Swift

Forty-eight hours to rebuild a real production screen in Flutter, test it, and ship it for a panel review. Nine teams. We wrote about 10,000 lines in two days, let Cursor generate roughly 80% of it, and placed 2nd.

The score is not the interesting part. What breaks when you lean on an AI agent under real time pressure, on code with deeply nested logic, while making decisions fast, is. Every item below cost us time before it saved us any. What follows is the workflow we ended up with, and why each piece earned its place.

We paired with Cursor for the whole sprint. This was an internal Flutter Workathon at slice, porting existing iOS screens Flutter-first.

Make it plan first#

The tempting move is to paste an error and say “fix this.” That is how we broke things in the first hour. The agent changes five files, three of them for reasons it invented, and now you have a new bug on top of the old one.

The prompt that fixed this for us:

Read the code. Understand the scope. Break it into steps. Suggest a plan, but do not touch the code yet.

That one instruction surfaces Cursor’s mental model before it acts, so you can correct a wrong assumption while it is still just text. We now do this even for tiny bugs. The plan takes thirty seconds to read and catches the “it misunderstood the whole task” case that otherwise eats an hour.

Validate every phase#

We had the screen rendering in a few hours. That velocity is addictive, and it is a trap. A bug we introduced in Phase 1 surfaced two phases later, tangled into everything built on top of it, and untangling it cost more than the head start ever bought.

The loop that kept us honest: prompt, test, validate, and only then move to the next phase. It feels slower. It is not. You are trading a satisfying speed you cannot trust for a real one you can.

Encode constraints as project rules#

Two separate mistakes taught the same lesson: Cursor will not guess your environment, and it will not respect your constraints unless you write them down.

We said “use flutter” and it happily used the wrong global version. The fix was to be specific (fvm flutter), but repeating that in every prompt is its own tax. So we moved it into a Cursor project rule. Set once, applied for the whole team.

The rules that earned their keep:

After making code changes, analyze the full project for compile errors.

That one caught breakages before runtime more times than we could count. When an agent edits across files, it will confidently leave one of them not compiling.

For API models, use only the fields present in the provided JSON. Do not infer or add anything.

We would hand Cursor a clean JSON payload and it would invent three extra fields that sounded plausible and did not exist. A rule that says “use only these keys, do not add anything” ends it. The pattern underneath both rules is the same: be painfully explicit up front, or debug the ambiguity later.

One task, one window#

We ran a single long thread through six context shifts. By the end it was blending assumptions across steps, hallucinating decisions we never made, and breaking logic it had written correctly an hour earlier. Long threads rot.

Now it is one window per task, short prompt history, tightly scoped context. Cleaner conversations, fewer side effects. A fresh window costs nothing and starts the agent from a clean slate instead of a polluted one.

Models are not interchangeable#

Different models differ in both quality and cost, and Cursor prices requests at different multipliers (some 1x, some 2x, some fractions of that). Leave Auto Mode and Max Mode on and you will exhaust your quota without understanding why. Max Mode goes big on the context window, which is expensive and rarely what you need. We learned that by burning through our quota in two days.

What we settled on during the sprint:

  • Claude Sonnet as the default for coding. Strong on structured refactors, low hallucination.
  • Claude Sonnet with thinking for planning. Better reasoning, roughly 2x the cost, so only when the plain model was not getting there.
  • GPT for docs, summaries, and rewriting our own messy prompts into something the coding model understood cleanly. For code it was hit or miss for us.
  • Gemini Flash for anything fast and disposable, though we rarely accepted its output once it touched multiple files.

The point is not this exact lineup, which will be stale in a month. The point is to pick a default you trust for the bulk of the work and reach for a pricier model deliberately, not automatically.

You run the terminal#

We watched Cursor hallucinate command chains, delete files it should not have, and reach for a force push. Let the AI suggest terminal commands all it wants. You run them. Every time. This is the one rule with no exceptions, because the blast radius of a wrong terminal command is the whole repo.

Stay hands-on with the code#

The real risk is not a bad diff. It is looking at a good one and realizing you no longer understand what changed. If a task is small and you already know the fix, write it yourself, counterintuitive as that sounds when an agent is sitting right there. You are augmenting your thinking, not outsourcing it.

Shipping with AI is easy. Shipping code that is correct, maintainable, and explainable by the person who “wrote” it is the hard part, and it is entirely on you.

The tool did not make us faster because it wrote code. It made us faster because we built a workflow that kept us in control of code it wrote: plan first, validate each phase, constrain it with rules, and never hand it the keys to the terminal. Treat it as a dev partner whose work you own, and the 80% it generates is a head start instead of a liability.
