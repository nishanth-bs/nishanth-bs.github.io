The chat outbox: designing offline sync that survives a dead network

The interview prompt is one line: “Design WhatsApp-style offline messaging for iOS.” You tap send on the subway, the message shows a clock, and three stops later it turns into a double tick. Simple to describe. The whole problem lives in what has to be true for that tick to be honest.

Here is the version most candidates draw first:

final class MessageQueue {
    private var messages: [Message] = []
    func enqueue(_ m: Message) { messages.append(m) }
    func dequeue() -> Message? { messages.isEmpty ? nil : messages.removeFirst() }
}

Spot the two bugs before reading on. One loses messages. The other duplicates them. By the end you will have the outbox and the client-side dedup key that kill both, and a status machine that can only move forward.

The queue lives in RAM, so it dies with the app#

An in-memory queue is a promise you cannot keep. The user is offline, taps send, the bubble shows “sending”. iOS gets a memory warning and kills your suspended app. That array is gone. When the user reopens the chat, the message is not pending, not failed, not anywhere. It just evaporated, after the UI already told them it was on its way.

The fix is boring and non-negotiable: persist the message before you render a single tick. The outbox is a table on disk, not an array in a manager. Core Data, SQLite, GRDB, whatever you already run. The message becomes durable the instant the user hits send, and the UI reads its state from that row.

// The row we write BEFORE showing anything in the UI.
struct OutboxMessage {
    let clientId: UUID          // generated on-device, at compose time
    let conversationId: UUID
    let body: String
    var status: MessageStatus   // starts .pending
    let createdAt: Date
    var attemptCount: Int
}

func send(_ body: String, to conversationId: UUID) throws {
    let msg = OutboxMessage(
        clientId: UUID(),
        conversationId: conversationId,
        body: body,
        status: .pending,
        createdAt: Date(),
        attemptCount: 0
    )
    try store.insert(msg)   // durable first
    render(msg)             // UI reads the row, shows the clock
    drainOutbox()           // try to send now if we can
}

Write the row, then show the clock. Now an app kill is survivable: on next launch you re-read every .pending row and drain them. The outbox is the source of truth; the bubble is a view of it.

“Sent” is a lie without a dedup key#

Here is the bug that ships to production and generates the “why did I send that twice” support tickets. Watch the send path on a flaky network:

func upload(_ msg: OutboxMessage) {
    api.post("/messages", body: msg) { result in
        switch result {
        case .success: store.update(msg.clientId, status: .sent)
        case .failure: store.update(msg.clientId, status: .failed) // will retry
        }
    }
}

The message reaches the server. The server writes it and sends back 200 OK. On the walk back through a dying LTE cell, the response is lost. The client never sees success, so it retries. Now the same message is on the server twice.

This is not an edge case. Any at-least-once delivery path hits it. You cannot make the network exactly-once, so you stop trying. The client generates the message ID, and the server dedups on it.

// The clientId we already put on the row IS the idempotency key.
// Server upserts on it, so a retry is a no-op, not a duplicate.
func upload(_ msg: OutboxMessage) {
    var body = MessagePayload(from: msg)
    body.idempotencyKey = msg.clientId        // same key across every retry
    api.post("/messages", body: body) { result in
        switch result {
        case .success:
            store.update(msg.clientId, status: .sent)
        case .failure(let error) where error.isRetryable:
            store.update(msg.clientId, status: .failed)   // retried later, SAME key
        case .failure:
            store.update(msg.clientId, status: .failedPermanent)
        }
    }
}

The retry carries the same clientId it carried the first time. The server sees a key it already stored and returns the existing message instead of creating a new one. At-least-once on the wire plus an idempotent server gives you effectively-once for the user. That is the whole trick, and it is worth saying in the interview out loud: you do not get exactly-once from the network, you buy it with a dedup key.

Status only moves forward#

A message walks through states. The mistake is treating status as a free-form string you can set from anywhere (the draft used var status: String). Then a late-arriving “sent” callback overwrites a “read” you already got from the server, and the double tick flickers back to a single clock in front of the user.

Model it as an enum with a rank, and refuse to go backward:

enum MessageStatus: Int, Comparable {
    case pending = 0      // in the outbox, not yet acked
    case sent = 1         // server has it
    case delivered = 2    // recipient's device has it
    case read = 3         // recipient opened it
    case failed = -1      // send failed, retryable

    static func < (a: MessageStatus, b: MessageStatus) -> Bool {
        a.rawValue < b.rawValue
    }
}

func apply(_ next: MessageStatus, to clientId: UUID) {
    guard var msg = store.message(clientId) else { return }
    // Forward-only, except a send in flight (.pending) may drop to .failed.
    guard next > msg.status || (next == .failed && msg.status == .pending) else {
        return  // reject stale callbacks: a late "sent" can't stomp a "read"
    }
    msg.status = next
    store.update(msg)
}

The guard is the point. Out-of-order acks arrive constantly (delivered and read receipts race the sent ack over different sockets). Forward-only status means a stale “sent” cannot stomp a “read”. failed is the single sanctioned way back, and only from pending.

stateDiagram-v2
    [*] --> pending
    pending --> sent
    pending --> failed
    failed --> pending: retry
    sent --> delivered
    delivered --> read
    read --> [*]

A stuck message must not block the ones behind it#

Order matters in chat, so the tempting design sends strictly one at a time and only advances after the current message is acked. That is exactly what creates head-of-line blocking: when the front message keeps failing, the drain keeps retrying it and never reaches the messages the user typed after it. It is the difference between “one message shows a red retry” and “the whole conversation freezes”.

// Serial and success-gated: message N+1 never starts until N is acked.
func drainSerial() {
    guard let msg = store.oldestPending() else { return }
    send(msg) { result in
        switch result {
        case .success:
            self.drainSerial()                       // move on to the next message
        case .failure:
            self.retry(msg) { self.drainSerial() }   // keep retrying THIS one first
        }
    }
}

A stuck front message loops on itself forever, and everything behind it waits.

Drain the outbox as independent rows, not a strict queue you pop. A failed message drops to .failed and stays visible with a retry affordance; the drain moves on to the next .pending row.

func drainOutbox() {
    let pending = store.messages(status: .pending)
        .sorted { $0.createdAt < $1.createdAt }   // FIFO intent, per conversation
    for msg in pending {
        upload(msg)   // one failing message marks itself .failed; the loop continues
    }
}

You keep per-conversation ordering as intent, and you accept that a failed message can end up behind newer ones after its retry. That is the real tradeoff to name in the interview: strict ordering or liveness, pick one when a message is stuck. Chat picks liveness and shows the failed bubble in place.

Reachability: drain on the edge, not on a timer#

The draft leaned on a Reachability class and a polling timer. There is no Reachability type in the SDK (it is the name of a popular third-party library and an old Apple sample). The first-party tool is NWPathMonitor, and it pushes you a signal instead of making you poll.

import Network

let monitor = NWPathMonitor()
monitor.pathUpdateHandler = { [weak self] path in
    if path.status == .satisfied { self?.drainOutbox() }  // network came back
}
monitor.start(queue: .global(qos: .utility))

One caveat worth stating: path.status == .satisfied means there is a route, not that your server answers. Captive portals and dead backends both look “satisfied”. So the outbox does not trust the monitor as proof of delivery. The monitor is a hint to try now; the only thing that moves a message to .sent is a real ack carrying the idempotency key. If the send fails anyway, the row goes back to .failed and waits for the next hint.

The payload#

Three rules carry the whole design. Persist before you promise so an app kill cannot vaporize a message the UI already acknowledged. Dedup with a client-generated key so an at-least-once retry cannot duplicate what the server already stored. Let status move only forward so a racing stale ack cannot flicker a read back to a clock.

The same idempotency-key idea shows up the moment you send binary instead of text. We take it apart for large media, background transfers, and app kills mid-upload in designing chat media upload.
