Chat Uploads That Outlive the App

July 4, 2026 · 7 min · Beyond Swift

The interview prompt: “Design media upload for a WhatsApp-style chat.” A user picks a 40MB video, sees a thumbnail with a progress ring, then switches to another app to take a call. iOS suspends your app, and may terminate it under memory pressure. When they come back, the video is sent. Nothing in that sentence is hard until the app leaves the foreground.

Here is the instinct most candidates reach for, and it is the wrong tool:

// Reaching for BGTaskScheduler to keep an upload alive in the background.
BGTaskScheduler.shared.register(forTaskWithIdentifier: "com.app.upload", using: nil) { task in
    // upload the video here...
}

BGTaskScheduler is for short, deferrable maintenance work: refresh a feed, clean a cache, a few tens of seconds the system grants when it feels like it. A 40MB upload over a bad cell is neither short nor schedulable on the system’s whim. By the end you will know the one API that actually survives backgrounding and app termination, the two constraints it forces on you, and why a retry can double your user’s media if you skip one field.

Only a background URLSession survives#

A background-configured URLSession hands the transfer to a separate system daemon (nsurlsessiond). It keeps running after your app is suspended, and it keeps running after the system terminates your app to reclaim memory. That is the property you need and the one BGTaskScheduler does not give you.

One boundary to state up front, because an interviewer will probe it: this survives system-initiated suspension and termination, not a user force-quit. When the user swipes your app out of the multitasking switcher, the daemon cancels every task in your background session with NSURLErrorCancelled. Force-quit is the user saying “stop”, and iOS honors it.

let config = URLSessionConfiguration.background(withIdentifier: "com.app.chat.upload")
config.isDiscretionary = false          // send now, not when the system prefers
config.sessionSendsLaunchEvents = true  // relaunch the app when the transfer finishes
let session = URLSession(configuration: config, delegate: self, delegateQueue: nil)

The identifier is not cosmetic. It is how you reattach to an in-flight transfer after the app dies and relaunches. Reuse the exact same string; do not generate a fresh one per upload.

Constraints the background session forces#

Move to a background session and two things that compiled fine on the foreground session now break. Both are worth stating in the interview because they trip up people who have only used URLSession.shared.

One: you must upload from a file on disk, not from Data in memory. The daemon runs the transfer while your process is dead. It cannot reach into your heap. So a Data body is not allowed: it throws NSGenericException at runtime (“Upload tasks from NSData are not supported in background sessions”). You hand it a file URL instead.

// Runtime crash on a background session: the daemon can't read your process memory.
let task = session.uploadTask(with: request, from: videoData)   // wrong

// Works: the daemon owns the file and streams it even after the app is killed.
let task = session.uploadTask(with: request, fromFile: localVideoURL)  // better
task.resume()

Two: you must use the delegate API, not a completion handler. This one is not a style choice. Calling the completion-handler variant on a background session throws at runtime.

// Runtime trap on a background session:
// "Completion handler blocks are not supported in background sessions."
session.uploadTask(with: request, fromFile: url) { data, resp, err in ... }  // crashes

// The delegate is the only supported shape. Results arrive here, maybe after relaunch.
func urlSession(_ s: URLSession, task: URLSessionTask,
                didCompleteWithError error: Error?) { ... }

The reason is the same as constraint one: a closure lives in your process, and your process may not exist when the transfer completes. The delegate is a class the system can hand results to on a freshly relaunched app.

When the app dies mid-upload#

This is the part that separates a working design from a demo. The transfer finishes while your app is terminated. iOS relaunches your app in the background specifically to deliver the result, and it gives you a narrow contract to honor.

sequenceDiagram
    participant App
    participant daemon as nsurlsessiond
    participant Server
    App->>daemon: uploadTask(fromFile:), resume()
    Note over App: app suspended, iOS terminates it under memory pressure
    daemon->>Server: keeps streaming the file
    Server-->>daemon: 200 OK
    daemon->>App: relaunch in background
    App->>daemon: recreate session (same identifier)
    daemon-->>App: didCompleteWithError + didFinishEvents
    App->>daemon: call stored completion handler

You implement the app-delegate hook, stash the system’s completion handler, recreate the session with the same identifier so its delegate fires, and call the stored handler once the session says it has drained every event.

// AppDelegate: the system calls this on background relaunch.
func application(_ application: UIApplication,
                 handleEventsForBackgroundURLSession identifier: String,
                 completionHandler: @escaping () -> Void) {
    // Stash it; call it later when the session is done delivering.
    UploadCoordinator.shared.backgroundCompletion = completionHandler
    UploadCoordinator.shared.reconnect(identifier: identifier)  // recreate the SAME session
}

extension UploadCoordinator: URLSessionDelegate {
    // Called once all queued delegate messages for this session are delivered.
    func urlSessionDidFinishEvents(forBackgroundURLSession session: URLSession) {
        DispatchQueue.main.async {
            self.backgroundCompletion?()   // let the system re-suspend us cleanly
            self.backgroundCompletion = nil
        }
    }
}

Skip the stored completion handler and the system marks your app as misbehaving and throttles future background time. Recreate the session with a new identifier instead of the original and your delegate never fires, so the result vanishes. Same identifier, call the handler, done.

Progress without a closure#

The foreground pattern is a progress closure. Background sessions do not have one, because there is no closure to call while you are suspended. Progress arrives through the delegate, and you total the bytes yourself.

func urlSession(_ session: URLSession, task: URLSessionTask,
                didSendBodyData bytesSent: Int64,
                totalBytesSent: Int64,
                totalBytesExpectedToSend: Int64) {
    let fraction = Double(totalBytesSent) / Double(totalBytesExpectedToSend)
    DispatchQueue.main.async { self.updateRing(for: task.taskIdentifier, fraction) }
}

The ring only animates while the app is in the foreground; once suspended, there is no UI to update anyway. When the app relaunches, you read the final state from your own outbox row rather than expecting a stream of progress you missed.

Thumbnails off the main thread#

The user should see the media instantly, well before a byte leaves the device. Generate a local thumbnail at pick time and render it under the progress ring. For video, the trap is the synchronous generator: copyCGImage(at:actualTime:) decodes on the calling thread and stalls the UI on a large file.

import AVFoundation

func thumbnail(for videoURL: URL) async throws -> UIImage {
    let asset = AVURLAsset(url: videoURL)
    let generator = AVAssetImageGenerator(asset: asset)
    generator.appliesPreferredTrackTransform = true   // respect recorded orientation
    generator.maximumSize = CGSize(width: 400, height: 400)
    // Async API (iOS 16+): decodes off the calling thread, no main-thread stall.
    let (cgImage, _) = try await generator.image(at: CMTime(seconds: 0.1, preferredTimescale: 600))
    return UIImage(cgImage: cgImage)
}

For a still image you are resizing, UIGraphicsImageRenderer replaces the old UIGraphicsBeginImageContext dance and is the current API. Do the resize once, cache the small version, and never hold the full-resolution image in the message list.

Retries double media without a key#

Uploads inherit the exact problem text messages have. The transfer completes on the server, the ack is lost, the client retries, and now there are two copies of the same 40MB video in the chat. The daemon retrying across an app kill makes this more likely, not less.

The fix is the same key we used for text: an idempotency key the client generates once and sends on every attempt. For media it is natural to derive it from the content itself.

// Same clientId as the message row; a content hash also works and dedups
// identical files across resends.
request.setValue(msg.clientId.uuidString, forHTTPHeaderField: "Idempotency-Key")

Same key on the retry, server upserts, one video. We work through why an at-least-once network cannot give you exactly-once, and how the client-generated key buys it back, in the chat outbox for offline sync.

The payload#

Media upload is not a networking problem, it is a survive-the-app-dying problem. Use a background URLSession, not BGTaskScheduler, because only the daemon keeps streaming after termination. Upload from a file with the delegate API, because the closure and the in-memory Data both assume a process that no longer exists. Honor the relaunch contract by reattaching with the same identifier and calling the stored completion handler. And key every upload so the retry that survives the app kill does not leave two videos in the chat.
