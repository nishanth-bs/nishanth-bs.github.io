The coordinator pattern's quiet memory leak

July 6, 2026 · 5 min · Beyond Swift
📊 ~... unique reads
Table of Contents

Here is the coordinator every UIKit app grows into. A parent holds its children in an array and starts a new one whenever it pushes a flow.

protocol Coordinator: AnyObject {
    var childCoordinators: [Coordinator] { get set }
    func start()
}

final class AppCoordinator: Coordinator {
    var childCoordinators: [Coordinator] = []
    let nav: UINavigationController

    init(nav: UINavigationController) { self.nav = nav }

    func showProfile() {
        let child = ProfileCoordinator(nav: nav)
        childCoordinators.append(child)   // retained here
        child.start()                     // pushes ProfileViewController
    }
}

A user opens a profile, taps back, opens another, taps back, and does it ten more times. Question before you scroll: how many ProfileCoordinator instances are alive now?

All twelve. This post is about why, and the delegate method that fixes it.

Where the retain comes from#

childCoordinators.append(child) is the only thing keeping the child alive, and it is also the only thing that ever touches that array. There is no matching remove.

So the array grows for the life of AppCoordinator, which is usually the life of the app. Every profile flow the user ever opened is still in memory: the coordinator, the view model it built, the network clients it holds, the image caches wired into them. Nothing is deallocated. Instruments shows a slow, sawtooth-free climb that most people blame on image loading.

The push side is symmetric and correct. The pop side is missing entirely.

The back button you do not own#

The reason it is easy to miss: you never wrote the pop. showProfile() is your code, so appending the child there is obvious. But the user leaves the profile by tapping the system back button, or by the interactive edge-swipe. UINavigationController pops the view controller for you. Your coordinator is never told.

So there is no natural place to call childCoordinators.removeAll { ... }, because the moment the flow ends is a moment your code does not run. A deinit on the child cannot help either: the child is what is leaking, so its deinit never fires.

You have to ask the navigation controller to tell you when a pop happened.

Releasing children on pop#

Make the parent the navigation controller’s delegate and watch didShow. When a view controller disappears because it was popped (not because a new one was pushed on top), free the child that owned it.

final class AppCoordinator: NSObject, Coordinator, UINavigationControllerDelegate {
    var childCoordinators: [Coordinator] = []
    let nav: UINavigationController

    init(nav: UINavigationController) {
        self.nav = nav
        super.init()
        nav.delegate = self
    }

    func start() { /* build and push the root, as before */ }

    func childDidFinish(_ child: Coordinator) {
        childCoordinators.removeAll { $0 === child }   // the missing half
    }

    func navigationController(_ navigationController: UINavigationController,
                              didShow vc: UIViewController, animated: Bool) {
        // the VC we transitioned away from; nil only when there is no
        // active transition, e.g. the initial root VC
        guard let fromVC = navigationController.transitionCoordinator?
                .viewController(forKey: .from) else { return }

        // still on the stack means it was pushed over, not popped
        if navigationController.viewControllers.contains(fromVC) { return }

        // fromVC was popped: release the child that manages it
        if let profileVC = fromVC as? ProfileViewController,
           let child = childCoordinators.first(where: { ($0 as? ProfileCoordinator)?.rootVC === profileVC }) {
            childDidFinish(child)
        }
    }
}

The two guards are the whole trick. viewController(forKey: .from) is the screen being left. It is non-nil on a push too, so the second guard does the real work: if that screen is still in viewControllers, something was pushed on top and the child is still in use. If it is gone from the stack, it was popped, and its coordinator can go.

Match the popped view controller back to its coordinator (here via a rootVC reference the child holds) and remove it. The array now shrinks when the user backs out one screen, including the edge-swipe you never see.

One caveat: .from gives you a single view controller, so this reclaims one coordinator per transition. A multi-level pop, popToRootViewController(animated:) or a long-press back-menu jump, surfaces only the immediate previous screen and silently strands the coordinators in between. If a flow can pop more than one level at once, reconcile the whole array against viewControllers in didShow instead of matching a single .from.

SwiftUI removes the object#

The leak exists because a coordinator is a long-lived reference type that has to be manually paired with a screen’s lifetime. SwiftUI’s NavigationStack (iOS 16+) deletes that whole category of bug by making navigation state a value. On earlier targets you are back in NavigationView, which has no value-based path and does not remove the leak the same way.

// User must itself be Hashable for the synthesized conformance to hold
enum Route: Hashable { case profile(User), settings }

struct RootView: View {
    @State private var path: [Route] = []   // the "stack" is just an array

    var body: some View {
        NavigationStack(path: $path) {
            HomeView()
                .navigationDestination(for: Route.self) { route in
                    switch route {
                    case .profile(let user): ProfileView(user: user)
                    case .settings:          SettingsView()
                    }
                }
        }
    }
}

There is no child object to retain, so there is nothing to forget to release. A back-swipe pops the last element off path, and the destination view (a struct) and anything it owned go away with it. The routing logic that lived in a coordinator moves into the Route enum and the binding.

Whichever world you are in, the lesson is the same: every place that starts a flow needs a matching place that ends it. In UIKit the ending place is the navigation delegate’s didShow, not your push code. Miss it and the pattern that was supposed to keep things tidy quietly holds onto everything.
