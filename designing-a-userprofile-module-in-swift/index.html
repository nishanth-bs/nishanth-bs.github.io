Modeling the Current User Without a Global Singleton

October 21, 2025 · 7 min · Beyond Swift
📊 ~... unique reads

Almost every app has the line. User.current, or Session.shared, or AppState.user. A global you can reach from anywhere that holds the logged-in user. It is the most convenient object in the codebase on day one and, a year later, the most coupled. The profile module is usually where the rot shows up first, because profile screens read and write the current user more than anywhere else.

The real question is not what goes in the UserProfile module. It is how the current user gets modeled and reached, because that one decision is what keeps the app testable or slowly strangles it.

What actually breaks#

Here is the convenient version. It passes review at a glance.

@MainActor
final class ProfileViewModel: ObservableObject {
    @Published private(set) var displayName = ""

    func refresh() {
        displayName = User.current!.name   // reach into the global, force-unwrap
    }
}

Before reading on: what breaks this in a unit test, and what breaks it for a user who opens a deep link while signed out?

Four things, and they trace to one root cause. The current user is a global anyone can touch.

It is a hidden dependency. A view model that reads User.current has a dependency that does not appear in its initializer, its type, or anywhere you can see. You cannot tell what a type needs by looking at it, which is the property that makes code understandable. Multiply this across fifty types and the current user becomes an invisible wire running through the whole app.

It is untestable. To test a type that reads User.current, your test has to set global state, and now tests leak into each other and pass or fail depending on order. The moment two tests want different users, you are writing setup and teardown to scrub a global, which is exactly the friction that makes people stop writing tests.

It is mutable shared state. A static var read and written from multiple threads is a data race waiting to happen. The profile screen mutating it on a background callback while another screen reads it on the main thread is the kind of bug that never reproduces on your desk.

It models “signed out” as nil. This is the quiet one. User? forces every call site to deal with the optional, so the codebase fills with User.current! (crashes when someone opens a deep link while logged out) or optional-chaining noise that hides the real question: what should the app do when there is no user?

Model identity as state#

Start by naming the thing you actually have. You do not have an optional user. You have a session that is in one of a few states.

enum Session {
    case signedOut
    case signedIn(User)
}

This reads better at every call site, because “signed out” is now a real case you handle rather than a nil you forgot about. And it leaves room for the states a real app grows into: signingIn, or signedIn(User, expiring: Bool) when a token is about to lapse. An optional cannot express any of that.

While you are here, separate two things that the word “user” usually smears together:

  • Identity: who you are. A stable id, the auth token, the things that define the session.
  • Profile: your display data. Name, avatar, bio, the things that change and that other people can see.

They have different lifetimes and different update paths. Identity changes at login and logout. Profile changes when the user edits their name or the server sends new data. Conflating them into one User blob is why a profile-photo update ends up touching auth code.

Inject the session as a dependency#

The fix for the hidden-dependency and testability problems is the same move: stop reaching for a global, and pass the session in. Define a small protocol for what consumers actually need.

protocol SessionProviding {
    var session: Session { get async }
    func sessionUpdates() async -> AsyncStream<Session>   // login/logout changes
}

The getters are async on purpose. The one real owner will be an actor (more on that below), and an actor’s state is only reachable with await. The protocol says so up front rather than pretending the read is free.

A view model now declares its dependency in the open, and a test hands it a stub with whatever session it wants, no global to scrub.

@MainActor
final class ProfileViewModel: ObservableObject {
    @Published private(set) var displayName = ""

    private let provider: SessionProviding
    init(provider: SessionProviding) { self.provider = provider }

    func start() {
        Task {
            apply(await provider.session)
            let updates = await provider.sessionUpdates()
            for await session in updates { apply(session) }
        }
    }

    private func apply(_ session: Session) {
        switch session {
        case .signedOut: displayName = ""
        case .signedIn(let user): displayName = user.name
        }
    }
}

The view model reacts to login and logout for free, because it observes the stream instead of reading a snapshot once. No NotificationCenter names to keep in sync, no manual “did the user change” checks scattered around.

The session store#

There is still exactly one owner of the current session. The difference is that it is a real object with a controlled surface, not a static var anyone can poke. An actor is the natural fit, because the whole point is safe access from anywhere.

actor SessionStore: SessionProviding {
    private var _session: Session = .signedOut
    private var continuations: [UUID: AsyncStream<Session>.Continuation] = [:]

    var session: Session {
        get async { _session }
    }

    func signIn(_ user: User) { update(.signedIn(user)) }
    func signOut() { update(.signedOut) }

    private func update(_ new: Session) {
        _session = new
        for c in continuations.values { c.yield(new) }
    }

    func sessionUpdates() -> AsyncStream<Session> {
        // makeStream hands us the continuation directly, so we register it from
        // inside the actor instead of touching actor state in AsyncStream's
        // @Sendable build closure (which would be a data race).
        let (stream, continuation) = AsyncStream<Session>.makeStream()
        let id = UUID()
        continuations[id] = continuation
        continuation.yield(_session)   // hand over the current state right away
        continuation.onTermination = { [weak self] _ in
            Task { await self?.removeContinuation(id) }   // drop a cancelled subscriber
        }
        return stream
    }

    private func removeContinuation(_ id: UUID) {
        continuations[id] = nil
    }
}

Reads and writes are serialized by the actor, so the data race is gone by construction. There is one writer path (signIn / signOut), so you always know how the session can change, which you never know with a public mutable global. And each stream cleans up after itself: onTermination fires when a subscriber’s task is cancelled or finishes, so observers that walk away do not pile up dead continuations in the dictionary.

graph TD
    Store[SessionStore: single owner] -->|injected as SessionProviding| P[Profile feature]
    Store -->|injected| F[Feed feature]
    Store -->|injected| S[Settings feature]
    Auth[Auth flow] -->|signIn / signOut| Store

The shape is the same as before, one current user, but the wire is now explicit and one-directional. Features receive a contract, auth is the only thing that writes, and nobody reaches into a global.

Logout is a teardown problem#

The moment that exposes whether your model is sound is logout. When the session goes to signedOut, every cache, every in-flight request, every screen holding user data has to be invalidated. With a global singleton this is a manual checklist that someone always forgets an item on, and the classic bug is the next user seeing a flash of the previous user’s data.

When the session is an observed stream, teardown becomes a reaction instead of a checklist: caches and stores subscribe to sessionUpdates, and clear themselves on signedOut. You still have to be thorough, but the propagation is automatic rather than something each feature has to remember to wire into the logout button.

When a singleton is actually fine#

This is worth the cost when the current user is read in many places, when you want testable feature code, or when login and logout need to ripple through the app. For a small app with one screen behind a login and no real test suite, a single injected store is still nicer than a global, but the actor and the streams are more machinery than the problem deserves. The line to watch for is the third or fourth User.current reference showing up in unrelated files. That is the app telling you the identity needs a real owner, before the convenience hardens into the most-coupled object you have.
