How big is an enum with associated values?

May 12, 2025 · 5 min · Beyond Swift
📊 ~... unique reads

Here is a four-case enum for an image cell, the kind that ships in every feed. Right now the value is in the .idle case, holding nothing at all. How many bytes does that empty value occupy?

struct Bitmap {                       // 64 bytes, stored inline
    var pixels: (UInt64, UInt64, UInt64, UInt64,
                 UInt64, UInt64, UInt64, UInt64)
}

enum ImageState {
    case idle
    case loading(progress: Double)    // 8 bytes
    case ready(Bitmap)                // 64 bytes
    case failed(code: Int)            // 8 bytes
}

Most people answer “a few bytes, it’s empty.” The real answer is 72. By the end you will know why an idle enum carries the weight of its heaviest sibling, and the one keyword that cuts it back down.

An enum is its fattest case#

A Swift enum reserves enough inline storage for its largest associated value, in every case. It is a value type, so the whole thing gets copied by value wherever it goes: assignment, function arguments, array elements. The case tag picks which interpretation is live, but the box is always sized for the biggest tenant.

Run it:

MemoryLayout<ImageState>.stride   // 72

That 72 is the 64-byte Bitmap payload plus a discriminator byte, rounded up to the type’s 8-byte alignment. (The exact figure is current-compiler layout, not an ABI guarantee, but the shape holds: fattest payload, plus a tag, aligned.) The .idle case stores no data and still travels in a 72-byte value, because an array of ImageState has to leave room for the one element that might be .ready.

This is the part that bites at scale. A [ImageState] with 10,000 cells is 720 KB of contiguous storage even if every cell is .idle, and every reassignment copies the full stride. The fix is not to avoid enums. It is to notice which payload set the size.

Two different things can keep a payload small, and it helps to keep them apart. .loading and .failed are small because Double and Int are themselves small value types, 8 bytes each, stored inline. Bitmap is expensive for the opposite reason: it is a large value type, and value types live inline in the enum. The other way to stay small is a heap-backed handle. A String or [Item] payload is an 8-byte reference into heap storage, so case ready([Item]) would cost 8 bytes inline no matter how many items the array holds. When a payload is genuinely heavy, the fix is usually the same struct-versus-class tradeoff from value types versus reference types: put the weight behind a reference so the enum only carries a pointer.

Spare bits make Optional free#

The discriminator does not always cost a byte. When a payload leaves some bit patterns unused, the compiler stores the tag inside those unused patterns instead of appending storage. This is the extra-inhabitants optimization, and Optional is where you see it most.

Optional is itself just an enum, the same shape covered in what Swift’s Optional really is:

enum Optional<Wrapped> {
    case none
    case some(Wrapped)
}

So .none needs a bit pattern that Wrapped never produces. Watch what that buys:

MemoryLayout<Bool>.size          // 1
MemoryLayout<Bool?>.size         // 1  (Bool only uses 0 and 1; .none reuses another pattern)

MemoryLayout<UInt8>.size         // 1
MemoryLayout<UInt8?>.size        // 2  (UInt8 uses all 256 patterns; .none needs a new byte)

MemoryLayout<UnsafeRawPointer?>.size   // 8  (a pointer is never null; .none == 0x0, free)

Bool? is the same size as Bool because Bool wastes 254 of its 256 patterns, and .none grabs one of them. UInt8? grows because UInt8 is fully inhabited, leaving no pattern to steal. A class reference optional is free for the same reason a pointer is: the reference is never zero, so nil is just 0x0 and needs no extra bit.

The takeaway you can use: making a fully-inhabited value optional (an Int, a UInt8) actually widens it, while making a pointer or a Bool optional is free. When a hot struct has several Int? fields, that padding adds up.

indirect boxes the payload#

indirect moves a case’s payload to the heap and leaves a pointer inline. It exists so recursive enums can compile at all. A case whose payload directly contains the enum itself has no finite size:

enum Expr {
    case literal(Int)
    indirect case add(Expr, Expr)     // directly holds two Exprs: needs the box
}

Drop the indirect and the compiler stops you with “recursive enum ‘Expr’ is not marked ‘indirect’”. Without it, add would have to store two whole Expr values inline, each of which stores two more, with no bottom. The keyword boxes the case’s payload on the heap, so add holds two 8-byte pointers instead of two full Expr values, and the type has a finite size again.

One thing that trips people up: a collection payload does not need indirect. case array([Expr]) or case object([String: Expr]) compiles without it, because a Swift Array or Dictionary is already a fixed-size, heap-backed handle. The recursion runs through the collection’s own storage, not through the enum’s inline layout, so there is nothing infinite to size.

The non-obvious use is capping a fat case. Mark only the heavy case indirect and the whole enum shrinks to the size of its remaining inline payloads:

enum ImageState {
    case idle
    case loading(progress: Double)
    indirect case ready(Bitmap)       // boxed: 8-byte pointer inline, not 64 bytes
    case failed(code: Int)
}

MemoryLayout<ImageState>.stride       // 16, down from 72

Now the common small cases travel light. The 64-byte Bitmap lives on the heap and only the rare .ready value pays for an allocation. That is the trade: you spend a heap allocation and a pointer chase on the fat case to stop it from bloating every other case in the array.

The rule#

An enum is sized for its widest payload and copied whole, so a single fat inline case taxes every value of that type. Check MemoryLayout.stride when an enum flows through a large collection, keep heavy payloads behind a reference or indirect, and remember that optional-of-a-pointer is free while optional-of-an-Int is not.
