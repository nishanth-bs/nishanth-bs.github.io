Why your SwiftUI view model keeps resetting

July 6, 2026 · 5 min · Beyond Swift
📊 ~... unique reads

Here is a view model that fetches a list of jokes. It compiles, it passes review, and it ships in a lot of apps.

final class JokeViewModel: ObservableObject {
    @Published var jokes: [Joke] = []
    private var cancellables = Set<AnyCancellable>()

    func fetch() {
        JokeService.fetchJokes()
            .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in
                self?.jokes = $0
            })
            .store(in: &cancellables)
    }
}

struct JokeList: View {
    @ObservedObject var viewModel = JokeViewModel()   // note this line

    var body: some View {
        List(viewModel.jokes) { Text($0.text) }
            .onAppear { viewModel.fetch() }
    }
}

Now put JokeList inside a parent that has a search field, and type one character.

struct Screen: View {
    @State private var query = ""
    var body: some View {
        VStack {
            TextField("Search", text: $query)
            JokeList()
        }
    }
}

The list goes blank. The network call that was in flight is gone. What happened?

By the end you will know why @ObservedObject var vm = VM() throws your state away on every keystroke, and the one-keyword fix that a lot of MVVM-in-SwiftUI code is missing.

The setup that looks fine#

Typing in the TextField mutates query. That is @State, so SwiftUI re-evaluates Screen.body. Re-evaluating the body means constructing a fresh JokeList value.

JokeList is a struct. Constructing it runs its stored-property initializers, and one of them is = JokeViewModel(). So a brand new view model is allocated, with jokes back to [] and a fresh empty cancellables. The old view model, along with its in-flight subscription, is dropped.

@ObservedObject does not save you here. It watches whatever object it is handed for the lifetime of this struct value. It does not keep the object alive across re-renders, because the struct value itself does not survive the re-render.

Why a View is a value#

This is the part that trips people who came from UIKit. A UIViewController is a reference type you allocate once and hold. A SwiftUI View is a struct that SwiftUI builds and throws away constantly, sometimes many times per second. If you are fuzzy on why that distinction matters, we wrote about it in value types vs reference types.

The rule that falls out of it: any object you create inside a View’s initializer is recreated every time that view is rebuilt, unless SwiftUI is told to own it.

@ObservedObject does not tell SwiftUI to own anything. It is a subscriber, not an owner.

@StateObject owns it#

@StateObject (iOS 14+) is the keyword that makes SwiftUI hold the object across re-renders, tied to the view’s identity rather than to the struct value. Before it existed, @ObservedObject was all you had, which is why so much SwiftUI-1 code created objects the wrong way and got away with it until a re-render exposed the reset.

struct JokeList: View {
    @StateObject private var viewModel = JokeViewModel()   // better: SwiftUI owns this

    var body: some View {
        List(viewModel.jokes) { Text($0.text) }
            .onAppear { viewModel.fetch() }
    }
}

Same line, one word different. Now when Screen.body re-runs and builds a new JokeList struct, SwiftUI recognizes it as the same view by position and identity, and reuses the view model it already created. The jokes array survives. The in-flight fetch survives. Typing in the search field does nothing to the list, which is what you wanted all along.

The initializer expression is the giveaway for how differently they behave. @StateObject wraps = JokeViewModel() in an autoclosure and runs it exactly once, the first time the view appears. @ObservedObject runs it every time the struct is built.

When @ObservedObject is right#

@ObservedObject is not broken. It is for objects created and owned somewhere else and passed in.

struct Screen: View {
    @StateObject private var viewModel = JokeViewModel()   // owner creates it here

    var body: some View {
        JokeList(viewModel: viewModel)                     // hands it down
    }
}

struct JokeList: View {
    @ObservedObject var viewModel: JokeViewModel           // observes, does not own

    var body: some View {
        List(viewModel.jokes) { Text($0.text) }
    }
}

The split is ownership. The view that creates the view model uses @StateObject. Any child that receives it uses @ObservedObject. Get that backwards, create it with @ObservedObject, and you are back to the resetting bug. Create it in two places with @StateObject and you have two independent copies that never agree.

The init trap people miss#

@StateObject running its initializer only once has a sharp edge. If you pass a value into the view model at construction, the view model captures the first value forever and ignores later ones.

struct UserHeader: View {
    let userID: String
    @StateObject private var viewModel: UserViewModel

    init(userID: String) {
        self.userID = userID
        // runs once; a later userID never reaches the view model
        _viewModel = StateObject(wrappedValue: UserViewModel(userID: userID))
    }
    ...
}

Render UserHeader(userID: "A"), then re-render it with "B", and the view model still holds "A". This is not a bug in @StateObject; it is the ownership contract doing exactly what it promises. When the input can change, feed it in through body instead, with .onChange(of:) or a method call, so the live object reacts to the new value rather than trying to be reborn with it.

The whole model rests on ObservableObject and @Published firing changes correctly. If the Combine side of that is hazy, the Combine caveats post covers where those publishers surprise you.

Create with @StateObject, observe with @ObservedObject, and never put a = SomeClass() behind an @ObservedObject again.
