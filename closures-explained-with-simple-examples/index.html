How Closures Capture, and Why Your Screen Leaks

January 13, 2026 · 5 min · Beyond Swift
📊 ~... unique reads

Push a screen, pop it, push it again, and watch deinit never fire while memory climbs. That is the most common memory bug in iOS, and it almost always comes down to one thing a closure does quietly: capture. A closure grabs the things it references and keeps them alive. Get that wrong with a closure that outlives the call, and you have a view controller that can never deallocate.

By the end you will know which closures can leak (only some can), why they leak, and the exact fix. What a closure holds onto is the whole story, so start there.

Capture by reference, not value#

A closure does not snapshot the values it uses. It captures the variable, and sees later changes to it.

var count = 0
let printer = { print(count) }

count = 10
printer()   // 10, not 0

printer captured count the variable, so by the time it runs it sees 10. If you want the value frozen at definition time, you say so with a capture list:

var count = 0
let printer = { [count] in print(count) }   // captures a copy, now

count = 10
printer()   // 0

This is also why the “changing a variable after map affects the result” warning you see in tutorials is wrong. map runs immediately and synchronously, so the closure has already finished before you change anything. Capture-of-a-mutating-variable only bites when the closure runs later, which is exactly the case that also causes leaks.

Only escaping closures can leak#

Two flavors, and only one of them can wreck your memory.

  • Non-escaping runs and finishes before the function it was passed to returns. map, filter, sorted, forEach. They cannot form a lasting cycle because they do not outlive the call. A plain closure-typed parameter is non-escaping by default. (One gotcha: an optional closure parameter, (() -> Void)?, is implicitly escaping, because wrapping it in Optional puts it in an enum the compiler cannot prove stays on the stack.)
  • Escaping outlives the call. It gets stored and runs later: a completion handler, a stored callback, a Combine sink, a Task. The @escaping marker exists because it sticks around, and sticking around is what holds things alive longer than intended.

So capture and [weak self] only matter for escaping closures that get stored. A [weak self] inside a forEach is dead weight.

The retain cycle, concretely#

Read this. Push the screen, pop it. Does deinit run?

final class FeedViewController: UIViewController {
    var onRefresh: (() -> Void)?

    func setup() {
        onRefresh = {
            self.reload()
        }
    }
}

It never runs. The screen leaks every time it is shown.

Trace the ownership. self owns onRefresh (it is a stored property). onRefresh captures self strongly (it calls self.reload()). Each end holds the other alive, so neither refcount ever reaches zero.

graph LR
    VC[FeedViewController] -->|stores| C[onRefresh closure]
    C -->|captures strongly| VC

The symptom in a real app: push a screen, pop it, push it again, and deinit never prints while memory climbs. Instruments shows the view controllers stacking up. The cause is almost always a stored escaping closure (or a Combine subscription, a delegate, a timer) capturing self.

Breaking the retain cycle#

A capture list captures self without the strong hold.

onRefresh = { [weak self] in
    self?.reload()        // self is now Optional, nil if the screen is gone
}

[weak self] makes self an optional that becomes nil once the object deallocates. The closure no longer keeps it alive, so the cycle is broken. In async code you usually want to unwrap once at the top:

onRefresh = { [weak self] in
    guard let self else { return }
    self.reload()
    self.trackRefresh()
}

[unowned self] is the other option, and it is a loaded gun. It captures self without keeping it alive and without making it optional, so accessing it after self is gone crashes. Use it only when you are certain the closure cannot outlive self, which is rare enough that the honest default is: reach for weak, and justify unowned out loud if you ever use it. A crash you have to reason about is worse than an optional you have to unwrap.

What actually causes most cycles#

In real code the leak hides inside an API that stores the closure for you. A raw onRefresh property is easy to spot. The dangerous ones do the storing on your behalf, so no line reads like “keeping a strong reference here.”

The one we see most is a Combine sink stored in cancellables:

final class FeedViewModel {
    @Published var query = ""
    private var cancellables = Set<AnyCancellable>()

    func bind() {
        $query
            .debounce(for: .milliseconds(300), scheduler: RunLoop.main)
            .sink { results in
                self.reload(results)   // wrong: sink captures self strongly...
            }
            .store(in: &cancellables)  // ...and self owns cancellables. Cycle.
    }
}

self owns cancellables, cancellables holds the subscription, the subscription’s closure captures self. Same cycle as before, just spread across three lines that each look innocent. The fix is the same capture list:

.sink { [weak self] results in
    self?.reload(results)   // better: no strong hold, cycle broken
}
.store(in: &cancellables)

The same shape shows up in a stored completion handler, a repeating Timer (which retains its target or closure until you invalidate() it), and a notification or KVO token whose closure captures self. All escaping, all stored, all the same question: when you store a closure that touches self, ask whether you need [weak self]. When you pass a closure to map or a UIView.animate block that runs and finishes, you almost certainly do not.

Once you can spot the escaping, stored closure that captures self, you have found where screens leak, and [weak self] with a guard let self is the fix. Everything else about closures is syntax. (Capture matters a second time under Swift concurrency, where the question shifts from “does this leak” to “is what I captured safe to touch from another thread.” That is a different article.)
