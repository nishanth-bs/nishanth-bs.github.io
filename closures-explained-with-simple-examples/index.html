How Closures Capture, and Why Your Screen Leaks

January 13, 2026 · 5 min · Beyond Swift

Closures get introduced as “functions you can pass around,” which is true and also the least interesting thing about them. The part that decides whether your app leaks memory is capture: a closure quietly grabs the things it references and keeps them alive. Get that wrong with the wrong closure and you have the single most common memory bug in iOS, a view controller that never deallocates.

So let’s skip the map { $0 * 2 } tour and talk about what a closure actually holds onto.

Capture is by reference, and that surprises people#

A closure does not snapshot the values it uses. It captures the variable, and sees later changes to it.

var count = 0
let printer = { print(count) }

count = 10
printer()   // 10, not 0

printer captured count the variable, so by the time it runs it sees 10. If you want the value frozen at definition time, you say so with a capture list:

var count = 0
let printer = { [count] in print(count) }   // captures a copy, now

count = 10
printer()   // 0

This is also why the “changing a variable after map affects the result” warning you see in tutorials is wrong. map runs immediately and synchronously, so the closure has already finished before you change anything. Capture-of-a-mutating-variable only bites when the closure runs later, which is exactly the case that also causes leaks.

Escaping is the dangerous kind#

Closures come in two flavors and only one of them can wreck your memory.

A non-escaping closure runs and finishes before the function it was passed to returns. map, filter, sorted, forEach, all non-escaping. They cannot create a lasting reference cycle because they do not outlive the call. Function parameters are non-escaping by default.

An escaping closure outlives the call. It gets stored somewhere and runs later: a completion handler, a stored callback, a Combine sink, a Task. The compiler makes you mark these @escaping precisely because they stick around, and sticking around is what lets them hold things alive longer than you intended.

The practical takeaway up front: you only need to worry about capture and [weak self] for escaping closures that are stored. Sprinkling [weak self] inside a forEach is noise, and it signals you are guessing.

The retain cycle, concretely#

Here is the leak. An object owns a closure (stores it in a property), and the closure captures that same object strongly. Now the object keeps the closure alive, the closure keeps the object alive, and neither can ever be freed.

final class FeedViewController: UIViewController {
    var onRefresh: (() -> Void)?

    func setup() {
        onRefresh = {
            self.reload()   // closure captures self strongly
        }
    }
    // self owns onRefresh, onRefresh captures self. Cycle. This screen never deallocs.
}

    C -->|captures strongly| VC

The symptom in a real app: you push a screen, pop it, push it again, and deinit never prints. Memory climbs every time. Instruments shows the view controllers piling up. The cause is almost always a stored escaping closure (or a Combine subscription, or a delegate, or a timer) capturing self.

Breaking the cycle: weak and unowned#

A capture list lets you capture self without the strong hold.

onRefresh = { [weak self] in
    self?.reload()        // self is now Optional, nil if the screen is gone
}

[weak self] makes self an optional that becomes nil once the object deallocates. The closure no longer keeps it alive, so the cycle is broken. In async code you usually want to unwrap once at the top:

onRefresh = { [weak self] in
    guard let self else { return }
    self.reload()
    self.trackRefresh()
}

[unowned self] is the other option, and it is a loaded gun. It captures self without keeping it alive and without making it optional, so accessing it after self is gone crashes. Use it only when you are certain the closure cannot outlive self, which is rare enough that the honest default is: reach for weak, and justify unowned out loud if you ever use it. A crash you have to reason about is worse than an optional you have to unwrap.

What actually causes most cycles#

It is rarely a raw stored closure like the example. In real code the culprits are:

  • A Combine sink that captures self and is stored in cancellables.
  • A stored completion handler that captures self.
  • A repeating Timer, which holds its target or closure strongly until you invalidate it.
  • A notification observer or KVO token closure capturing self.

All of them are escaping and stored, which is the pattern to watch for. When you store a closure that touches self, that is the moment to ask whether you need [weak self]. When you pass a closure to map or a UIView.animate block that runs and finishes, you almost certainly do not.

A concurrency note#

Closures crossing concurrency boundaries add a second concern: data races. A @Sendable closure (the kind Task and other concurrency APIs often want) is not allowed to capture mutable shared state, because it might run on a different thread than the one it was created on. The compiler enforces it under strict concurrency checking. The capture question is no longer only about leaks. It becomes whether what the closure captures is safe to touch from another thread, and the value types we wrote about in The Hidden Cost of Value Types are a big part of why value semantics make that question easier to answer.

The summary worth keeping: closures capture variables by reference and keep them alive. Non-escaping closures finish before they could cause trouble. Escaping, stored closures that capture self are where screens leak, and [weak self] with a guard let self is the fix. Everything else about closures is syntax.
