How Swift and Objective-C see each other

July 5, 2026 · 5 min · Beyond Swift
📊 ~... unique reads

Your Swift class is public, the Objective-C file that needs it does #import "ShopKit-Swift.h", and the build fails: Cannot find interface declaration for 'OrderFormatter'. The class is right there in the same module, the header exists, and the compiler parsed it. So why is your class not in it?

Because the two languages do not read each other’s source. They meet through two generated artifacts pointing in opposite directions, and each one is gated by a build setting that has to be right. By the end you will know which artifact carries which direction, the setting that produces each, and why your @objc class can still go missing.

Two directions, two bridges#

Swift calling Objective-C and Objective-C calling Swift are not the same problem, and they do not use the same file. Mixing them up is why interop feels random.

flowchart LR
  ObjC["Objective-C code"] -->|bridging header| Swift["Swift code"]
  Swift -->|generated -Swift.h| ObjC

Swift reads Objective-C through a header you write. Objective-C reads Swift through a header the compiler writes. One is input, one is output, and each has its own settings and its own failure mode. The error above is on the second bridge.

Objective-C reads a generated header#

When Swift compiles, it emits an Objective-C header describing every Swift declaration it could expose. That file is -Swift.h, and your Objective-C imports it to see Swift types.

Its name is SWIFT_OBJC_INTERFACE_HEADER_NAME, defaulting to <ProductModuleName>-Swift.h. So a module named ShopKit produces ShopKit-Swift.h, imported two ways depending on where you are:

// inside the same app target
#import "ShopKit-Swift.h"

// from outside a framework
#import <ShopKit/ShopKit-Swift.h>

For a framework, that header is installed into the framework’s public interface only when SWIFT_INSTALL_OBJC_HEADER = YES (the “Install Objective-C Compatibility Header” setting, on by default) and DEFINES_MODULE = YES. Turn either off and an external #import <ShopKit/ShopKit-Swift.h> resolves to nothing, a file not found error. The header is still generated for the framework’s own .m files to use. Note that file-not-found is a different failure from the error at the top, where the header is found and your class is simply absent from it.

Not every Swift type crosses#

This is the failure from the top. The -Swift.h header carries only what Objective-C can represent, and a Swift class enters it in one of two ways:

// bridged automatically: rooted in an Objective-C class, so no @objc needed on the class
public class OrderFormatter: NSObject {
    @objc public func format(_ order: Order) -> String { … }  // members still need @objc (SE-0160)
}

// bridged only because it is marked: a class with no Objective-C superclass
@objc public class Coupon { … }

// never bridged, silently absent from -Swift.h:
public class PriceEngine { … }         // plain Swift class: no ObjC root, no @objc
public struct Money { … }              // structs cannot bridge
public enum Status { case open, shut } // non-@objc enums cannot bridge
public class Cart<Item> { … }          // generics cannot bridge

The class from the top was a plain Swift class: no Objective-C superclass and no @objc, so it was never a candidate for the header. The compiler does not error on the Swift side. It omits the declaration, the header parses fine without it, and Objective-C fails with “cannot find interface declaration.” A class rooted in NSObject bridges for free (the @objc on it would be redundant), but its individual members still need their own @objc since SE-0160, and in a framework the class must be public. When a type refuses to appear, the fix is on the Swift declaration, not the build settings.

Swift reads a header you write#

The other direction is the bridging header, SWIFT_OBJC_BRIDGING_HEADER. You list Objective-C headers in it, and everything they declare becomes visible to Swift in that target:

// ShopKit-Bridging-Header.h
#import "LegacyReceiptScanner.h"
#import "OldAnalytics.h"

Two constraints trip people up. A bridging header exists only for app and unit-test targets; frameworks do not use one. A framework exposes its Objective-C through its umbrella header and module map instead, which is why CLANG_ENABLE_MODULES = YES matters: Swift’s importer pulls Objective-C in as a Clang module, not as textual headers. (@import UIKit; is Objective-C’s spelling of a module import; in Swift you just write import UIKit.) Turn modules off and the Swift side loses visibility into the Objective-C it depends on.

The import cycle that will not build#

The two bridges can point at each other, and then neither builds. It looks like this: the bridging header imports an Objective-C header, and that Objective-C header imports the generated -Swift.h.

// LegacyReceiptScanner.h  (reached via the bridging header)
#import "ShopKit-Swift.h"   // depends on Swift compiling first

Swift needs the bridging header resolved before it can compile. The bridging header pulls in LegacyReceiptScanner.h, which pulls in ShopKit-Swift.h, which does not exist until Swift compiles. The dependency eats its own tail and you get a ShopKit-Swift.h file not found. On a machine with a stale header cached from a prior build it can look like it “fixes itself” on the second run, which is the confusing part. Clear DerivedData or run it on CI and it fails identically both times.

The break is to keep the generated header out of anything the bridging header can reach. Import -Swift.h only from .m implementation files, never from a .h that the bridging header pulls in. The same “the build lied, then the app broke” pattern shows up across the toolchain, as in the build passed and the app still crashed on launch.

Interop is two headers pointing opposite ways. When Objective-C cannot see your Swift, check the generated -Swift.h and whether your type can bridge at all. When Swift cannot see your Objective-C, check the bridging header, or the module map if it is a framework.
