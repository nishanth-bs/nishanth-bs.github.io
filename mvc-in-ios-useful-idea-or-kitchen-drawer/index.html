Why UIKit Breeds Massive View Controllers

February 10, 2025 · 9 min · Beyond Swift
📊 ~... unique reads

Every iOS team eventually fights the same file. A view controller that started small and is now four figures of line count, the one nobody volunteers to touch. The usual explanation is discipline: someone got lazy, nobody refactored. That explanation is comfortable and mostly wrong.

Massive View Controller is not a discipline failure. It is what UIKit’s design pushes you toward by default. Understand the mechanism and you stop fighting symptoms. First, why the controller becomes a magnet. Then what each escape hatch actually costs, because none of them are free.

Five responsibilities collide in the controller#

UIViewController is not one role. It is the single object where five separate UIKit responsibilities all converge, and the framework hands you that object as the entry point for every screen. That convergence is the whole problem.

graph TD
    VC[UIViewController]
    L[View ownership and lifecycle] --> VC
    TA[Target-action handlers] --> VC
    D[Delegate and data source conformance] --> VC
    N[Navigation and flow] --> VC
    R[Responder chain membership] --> VC

Before naming them, look at where they end up. Here is a ProfileViewController that started life as a plain detail screen:

final class ProfileViewController: UIViewController, UITableViewDataSource, UITextFieldDelegate {

    override func viewDidLoad() {                       // lifecycle
        super.viewDidLoad()
        saveButton.addTarget(self, action: #selector(didTapSave),   // target-action
                             for: .touchUpInside)
        load()
    }

    func tableView(_ t: UITableView,                    // data source
                   cellForRowAt indexPath: IndexPath) -> UITableViewCell {
        let cell = t.dequeueReusableCell(withIdentifier: "cell", for: indexPath)
        cell.textLabel?.text = format(rows[indexPath.row])   // ...and formatting sneaks in too
        return cell
    }

    @objc private func didTapSave() {
        service.save(draft)
        navigationController?.pushViewController(              // navigation
            ConfirmationViewController(), animated: true)
    }
    // it is a UIResponder too, so editing and events route through it as well
}

Run the interview question on it: which of these responsibilities actually belongs on this one object, and which would you move?

The honest answer is that every method has a defensible reason to be exactly where it sits. Nothing here is careless. That is what makes the class grow without anyone deciding to grow it. Walk the five responsibilities and the framework reason behind each one is right there.

1. View ownership and lifecycle. The controller is where UIKit hands you the view tree. loadView, viewDidLoad, viewWillAppear, traitCollectionDidChange, viewDidLayoutSubviews. These are not hooks you can relocate. The framework calls them on the controller, so any setup that depends on view timing starts here.

2. Target-action. button.addTarget(self, action: #selector(didTap), for: .touchUpInside). The action method has to be @objc and live on some object. The controller is right there, already retained for the lifetime of the screen, already in scope. So the handlers land on it, multiplied by every control.

3. Delegation and data sources. UITableViewDataSource, UITextFieldDelegate, UIScrollViewDelegate, UICollectionViewDelegateFlowLayout. Conforming is easiest when the conformer is the controller, because the data and the view are both already in scope. So data shaping, cell configuration, and interaction logic accrete onto the same object.

4. Navigation. navigationController?.pushViewController(...), present(...), segues. The controller knows the navigation stack, so “what happens next,” the branching and the deep-link handling, settles here too.

5. The responder chain. UIViewController is a UIResponder. Events, becomeFirstResponder, editing actions, and UIEvent handling route through it. It participates in input handling whether you asked it to or not.

Five responsibilities, one object, all in scope at once. For any new behavior, the path of least resistance is “put it on the view controller,” because the controller already references everything the behavior touches. That is the gravity. Not sloppy engineers, a framework that arranges the furniture so the easy move is the wrong one.

Object lifetime, the quieter pull#

There is a related reason logic ends up tangled here. The view controller has a clean, framework-managed lifetime that maps to the screen. Things that need that lifetime, observation, subscriptions, timers, get parked on it because it is the obvious owner.

That is also where the lifetime bugs come from. Anything that captures self and outlives a single call has to be careful:

// Combine subscription stored on the controller. Without [weak self],
// the sink retains the controller, and if the controller also owns the
// cancellable, you have a cycle that leaks the whole screen.
viewModel.$state
    .sink { [weak self] state in self?.render(state) }
    .store(in: &cancellables)

// Same story for a Task you kick off and the closures it captures.
loadTask = Task { [weak self] in
    let result = try await self?.service.load()
    self?.render(result)
}

This is not unique to MVC, but the controller’s role as the default owner of everything is what makes it the place leaks concentrate. More responsibilities on one object means more captures of self, means more places a missing [weak self] quietly retains an entire screen’s worth of views. We pulled apart exactly how that capture leaks a screen in How Closures Capture, and Why Your Screen Leaks.

Peel responsibilities off the controller#

Here is the mental shift that actually helps. The goal is not to escape UIViewController. UIKit requires it to exist and will keep calling its lifecycle methods. The goal is to move responsibilities off it, one at a time, and the right question is always “which of the five is hurting right now.”

graph TD
    VC[UIViewController: lifecycle only]
    VM[ViewModel: state and formatting]
    CO[Coordinator: navigation]
    DS[Diffable data source object: list data]
    VC --> VM
    VC --> CO
    VC --> DS

Each arrow off the controller is an escape hatch, and each one has a real price. Picking the wrong one, or all of them at once, trades Massive View Controller for a different mess.

MVVM moves state out#

Pull presentation state and formatting into a view model the controller observes. The win is genuine: the formatting and the loading/loaded/error logic become testable without UIKit, because the view model imports no UIKit.

@MainActor
final class ProfileViewModel: ObservableObject {
    enum State { case loading, loaded(ProfileFields), failed(String) }
    @Published private(set) var state: State = .loading

    private let service: ProfileService
    init(service: ProfileService) { self.service = service }

    func load() {
        state = .loading
        Task {
            do { state = .loaded(ProfileFields(try await service.fetch())) }
            catch { state = .failed("Could not load profile.") }
        }
    }
}

The single State enum is doing the real work: it makes loading, loaded, and failed mutually exclusive, so the contradictory isLoading == true while error != nil bug cannot compile. We go deeper on modeling a screen’s state as one value in Designing Data Flow From API to UI.

The cost: you still own the view controller, you now need a binding mechanism (Combine, or observation), and there is nothing stopping the view model from becoming a Massive View Model. MVVM moves the weight, it does not delete it. If your screen’s pain is untestable formatting and tangled state, this is the right first cut. If your pain is navigation, MVVM does nothing for you.

Diffable data source moves lists out#

When the controller drowns in cellForRowAt, section math, and snapshot juggling, that weight belongs to an object that owns the list. A UITableViewDiffableDataSource held by a small controller-of-the-list does exactly that:

// better: one object owns the snapshot, the view controller just hands it rows
final class ProfileListController {
    enum Section { case main }
    private let dataSource: UITableViewDiffableDataSource<Section, Row>   // Row is your Hashable row model

    init(tableView: UITableView) {
        dataSource = UITableViewDiffableDataSource(tableView: tableView) { table, indexPath, row in
            let cell = table.dequeueReusableCell(withIdentifier: "cell", for: indexPath)
            cell.textLabel?.text = row.title
            return cell
        }
    }

    func show(_ rows: [Row]) {
        var snapshot = NSDiffableDataSourceSnapshot<Section, Row>()
        snapshot.appendSections([.main])
        snapshot.appendItems(rows)
        dataSource.apply(snapshot, animatingDifferences: true)   // diffing and animation, not the controller's job
    }
}

The view controller drops its UITableViewDataSource conformance entirely and calls listController.show(rows). The cost is small and mostly upside: one more object, and you give up hand-rolled reloadData for diffing, which is usually what you wanted anyway.

Coordinators move navigation out#

A coordinator owns “what happens next.” The controller stops calling pushViewController and instead reports intent:

// wrong: the screen hard-codes the next screen, so the flow cannot be reused or rerouted
@objc private func didTapCheckout() {
    let next = CheckoutViewController(cart: cart)
    navigationController?.pushViewController(next, animated: true)
}

// better: the screen says what happened, the coordinator decides what is next
@objc private func didTapCheckout() {
    coordinator.didRequestCheckout(for: cart)
}

final class ShopCoordinator {
    private let navigationController: UINavigationController
    init(navigationController: UINavigationController) { self.navigationController = navigationController }

    func didRequestCheckout(for cart: Cart) {
        navigationController.pushViewController(CheckoutViewController(cart: cart), animated: true)
    }
}

The wins are real for anything with branching flows, reusable screens, or deep links, because flow logic stops being duplicated across the controllers that trigger it. The cost is indirection and lifetime management. Coordinators are plain objects with no framework-managed lifetime, so you have to retain them deliberately and tear them down correctly, which is its own class of bug (a coordinator that deallocates mid-flow, or one that never deallocates). Worth it when flows are complex or shared. Overhead when every screen is a dead end.

Adopting a full pattern#

VIPER-style layering (view, interactor, presenter, entity, router, all behind protocols) and paradigms like The Composable Architecture relocate everything at once instead of one responsibility at a time. On a large team with genuinely complex screens they buy real isolation and parallel work. The cost is the same in both cases: a file explosion, a steep onboarding tax, and boilerplate that exists to satisfy the pattern rather than a problem you actually have. Reach for them only when the team and the complexity together justify it, which is rarer than the tutorial count suggests. These are not a peel. They are a rewrite, and they are all-or-nothing across a codebase.

How to attack a massive controller#

Do not rewrite it. Name the responsibility that is hurting most right now (list shaping, tangled state, or duplicated navigation), peel that one off using the matching cut above, and stop. Each extraction is independent, so you can move the data source out and never touch navigation, or the reverse. What remains is a controller doing the one job UIKit actually demands: owning a view and its lifecycle.

MVC is not the villain here. For a small screen, Apple’s MVC is exactly the right amount of structure, and reaching for a coordinator or a paradigm on a two-field detail view is its own mistake. The judgment worth keeping is that the bloat is structural, not moral: the framework pulls five responsibilities onto one object on purpose, so the cure is removing whichever one is heaviest, not jumping to whatever architecture is fashionable this year.
