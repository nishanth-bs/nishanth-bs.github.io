The Hidden Cost of Value Types: Copy-on-Write, and When Structs Bite

December 9, 2025 · 5 min · Beyond Swift

“Use structs by default” is advice so repeated that nobody asks the obvious follow-up: what does the copy actually cost? Everyone can recite that structs copy and classes share. The part worth your attention is what “copy” means at runtime, when it is free, when it quietly is not, and the class of bug that shows up when you have lost track of which one you are holding.

We will assume you know the textbook difference. Assign a struct, you get an independent copy. Assign a class, both names point at the same instance. Here is everything past that.

The real feature is value semantics, not “avoiding ARC”#

People justify structs with “no reference counting overhead.” That is a minor perk. The actual win is that a value cannot be mutated behind your back. If a function takes a struct, nothing it does can change your copy. Two threads each holding a copy cannot race on it, because they do not share anything. You can reason about a value locally, which is the property large codebases are starved for.

That guarantee is the reason to default to structs. The performance argument is secondary and, as we will see, sometimes backwards.

But copying sounds expensive, so why is Array a struct?#

If structs copy on every assignment, an Array of 10,000 elements would be catastrophic to pass around. It is not, because the standard library’s collections (Array, Dictionary, Set, String) use copy-on-write.

A CoW type is a value type wrapped around a reference to a heap buffer. Assigning it does not copy the buffer. It shares it and bumps a reference count, which is O(1). The actual copy is deferred until someone mutates a buffer that is shared.

graph TD
    A["var a = [big array]"] --> Buf[heap buffer]
    B["let b = a (O(1), shares)"] --> Buf
    B -->|"b.append() while shared"| Copy[copies buffer first, then mutates]

Under the hood the check is reference uniqueness. On mutation, the type asks whether it is the only owner of this buffer. If yes, mutate in place. If no, copy the buffer, then mutate, so nobody else sees the change. You get value semantics with the cost of a copy paid only when it is actually needed.

Where copy-on-write quietly bites#

CoW is great until an accidental second reference turns cheap mutations into expensive ones. Consider:

var items = [/* 10k elements */]
let snapshot = items          // shares the buffer, fine

for i in 0..<items.count {
    items[i].flag = true       // first write copies the whole buffer, because snapshot still holds it
}

That first mutation copies all 10,000 elements, because snapshot is keeping the buffer non-unique. Hold a reference longer than you meant to, capture the array in a closure, stash it in a property, and you can pay for full copies you never see in the code. The fix is to not keep stray references alive across mutations, and to be aware that reading it into another variable is enough to trigger a copy on the next write.

Your own structs do not get copy-on-write for free#

This is the part that surprises people. CoW is hand-written in the standard library. Your struct does not have it. A plain struct copies all of its stored properties eagerly on every assignment and every function call.

For a small struct, who cares. Three Ints on the stack is nothing. But a struct with fifty stored properties, or one holding a large fixed buffer, copies all of it every single time you pass it to a function or assign it. That is the “structs are secretly expensive” case the performance folklore skips, and it is the real answer to “is a struct always faster than a class.” It is not. There is a size past which the copy costs more than a class’s allocation plus reference counting.

If you genuinely have a large value type that is copied a lot, you implement CoW yourself: back it with a class for storage and copy that storage only when it is shared.

struct BigValue {
    private final class Storage { var data: [Int]; init(_ d: [Int]) { data = d } }
    private var storage: Storage

    init(_ data: [Int]) { storage = Storage(data) }

    var data: [Int] {
        get { storage.data }
        set {
            if !isKnownUniquelyReferenced(&storage) {
                storage = Storage(storage.data)   // copy only when shared
            }
            storage.data = newValue
        }
    }
}

isKnownUniquelyReferenced is the same uniqueness check the standard library uses. Most code never needs this. Knowing it exists is what lets you fix the one screen where a fat value type is showing up in a profiler.

The leaky-value bug: a struct holding a class#

A struct gives you value semantics only if everything inside it does. Copy this one and predict what the last line prints:

final class Box { var value = 0 }
struct Holder { var box = Box() }

var a = Holder()
var b = a            // Holder is a struct. Copied, right?
b.box.value = 99
print(a.box.value)   // ?

It prints 99. The copy of Holder duplicated the box reference, not the Box it points at, so a and b share one object. The type reads like a value and behaves like a reference for that one property, which is exactly the kind of bug that survives review because the declaration says struct. If a struct needs to hold reference-type state and stay a true value, you are back to implementing CoW so the shared object is copied on mutation.

So which is actually cheaper#

Classes cost a heap allocation and ARC traffic, where retain and release are atomic operations that are not free under contention. Structs avoid that for their own storage and can live on the stack. But large structs cost copies, and structs holding class references still drag the heap and ARC in through the back door. The correct mental model is not “structs fast, classes slow.” It is that small values are cheap and safe, shared mutable objects are sometimes what you actually need, and the only way to know which is winning on a hot path is to measure it.

Default to structs for the value semantics, reach for a class when you need identity, shared mutable state, or inheritance, and remember that the copy you are not thinking about is the one that shows up in the profiler.
