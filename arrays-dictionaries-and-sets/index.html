What Swift's Collections Actually Cost: Buffers, Hashing, and the O(n) You Didn't See

“Use a Set when you need uniqueness, an Array when you need order.” Fine, true, and not the part that ever hurts you. The part that hurts is that Array, Dictionary, and Set each have a cost model you can read straight off how they store memory, and most of the performance bugs we have chased in real apps come from a line that looks O(1) and is secretly O(n). We will assume you know the API. Here is what it costs.

Array is contiguous, and that one fact is the whole story#

An Array is a single contiguous block of elements. Everything else follows from that.

Contiguous memory is why indexing is O(1): the address of element i is just base plus i times the stride. It is also why append is O(1) amortized and why iterating is cache-friendly and fast. So far so good.

The cost lands on any operation that has to move the block. removeLast() is O(1), because nothing shifts. removeFirst() is O(n), because every remaining element slides down one slot to keep the block contiguous:

var queue = [1, 2, 3, 4, 5]
queue.removeFirst()   // O(n): every element after it shifts left

These two read like mirror images and are nothing alike. We have seen an “event queue” built on removeFirst() in a loop turn into an accidental O(n²) drain that was invisible at ten events and a visible stall at ten thousand. If you want a FIFO, either drain from the back of a reversed array or reach for a structure that does not pay to shift.

The other contiguous-memory tax is contains:

let blockedIDs: [Int] = loadBlocklist()   // 10,000 ids
for event in incoming {                    // 10,000 events
    if blockedIDs.contains(event.id) {     // O(n) linear scan, every iteration
        continue
    }
}

That is 100 million comparisons for what feels like a filter. Array.contains walks the array. The fix is not a cleverer scan, it is a different container: build a Set of the ids once and the check drops to O(1). Reaching for Array.contains inside a loop is, in our experience, the single most common way iOS code goes quadratic without anyone noticing.

Capacity grows by doubling, so tell it the size once#

An array carries a count and a larger capacity. Append past capacity and it allocates a fresh buffer at roughly double the size, copies every element over, and frees the old one. Amortized that is O(1) per append, but “amortized” is hiding real reallocations: building a 100,000-element array from empty reallocates and copies on the order of 17 times on the way up.

If you know roughly how big it gets, say so:

var rows = [Row]()
rows.reserveCapacity(source.count)
for item in source { rows.append(transform(item)) }

One allocation instead of a dozen. This is close to the cheapest performance win Swift offers and almost nobody types it.

Dictionary and Set are the same machine: a hash table you co-own#

Dictionary and Set are the same thing underneath, a hash table with open addressing. The O(1) average lookup you lean on is not free magic. You are a co-owner of it, and you can break it two ways: with a bad hash, or with a key whose hash changes after you store it.

A weak Hashable degrades you to linear, silently#

Every lookup hashes the key, jumps to a bucket, compares. That stays O(1) only while distinct keys land in distinct buckets. Collapse many keys onto the same hash and they pile into neighbouring buckets, and lookups creep back toward linear. The usual way to cause this is hashing fewer fields than you compare:

struct CacheKey: Hashable {
    let userID: Int
    let locale: String
    let variant: Int

    // wrong: every key with the same userID hashes identically
    func hash(into hasher: inout Hasher) {
        hasher.combine(userID)
    }
}

The dictionary stays correct, because == still checks all three fields. It just gets slow, in a way that throws no error and crashes nothing. You feel it as a cache that mysteriously got expensive under load. The synthesized Hashable conformance hashes exactly the fields == compares, which is the real reason to delete the hand-written version and let the compiler do it.

Mutate a key’s hash after inserting and the element vanishes in place#

The hash is computed once, at insert, to pick the bucket. Change the key afterward so its hash changes and the element is now sitting in the wrong bucket. It is still in the collection. You just cannot find it.

You cannot trip this with a value-type key, since inserting copies it. With a class key you can, easily:

final class Node: Hashable {
    var id: Int
    init(id: Int) { self.id = id }
    static func == (l: Node, r: Node) -> Bool { l.id == r.id }
    func hash(into h: inout Hasher) { h.combine(id) }
}

var seen: Set<Node> = []
let n = Node(id: 1)
seen.insert(n)
n.id = 2              // changed a live key's hash
seen.contains(n)      // false: it is in the set, in the wrong bucket

Reference-type keys in a hashed collection are a footgun. If you are stuck with them, treat the hashed fields as frozen the moment you insert, or hash on an identifier that genuinely cannot change.

Iteration order is random, and it is random on purpose#

This is the one that ships. Dictionary and Set have no defined iteration order, and since Swift 4.2 the hasher is seeded with a per-process random value. Same binary, same data, fresh launch, different order.

let tags: Set = ["ios", "swift", "perf"]
for t in tags { print(t) }   // order changes between launches

So the snapshot test that serializes a dictionary to text and diffs it is green on your laptop and flaky in CI depending on the seed. The list you build by iterating a Set reorders itself between runs and a user files a bug. The “fingerprint” you compute by hashing iteration order is not reproducible. None of these are bugs in the collection. They are bugs in assuming an order the collection never promised. When order is observable, ask for it: dict.keys.sorted(), a parallel array of keys, or an ordered collection type.

The table worth pinning up#

Operation Array Dictionary / Set
Index access O(1) n/a
Membership / lookup by key O(n) via contains O(1) average
Append / insert O(1) amortized O(1) average
Remove first O(n) n/a
Remove last / arbitrary key O(1) O(1) average
Defined iteration order yes no

Read down the membership row and the whole thing collapses to one habit. If the hot path is “is this in here” and you do not need order, you want a hashed collection, not an array. That is the entire reason Set exists, and the copy-on-write machinery that makes all three cheap to pass around is the same in each, which we pulled apart in The Hidden Cost of Value Types.

The cost model was always sitting under the friendly API. Knowing it is the difference between code that profiles clean on your seed data and code that holds up when a real user hands it ten thousand of something.
