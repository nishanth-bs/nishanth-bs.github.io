The Architecture That Survives a Team Scaling From 5 to 20

July 15, 2025 · 4 min · Beyond Swift

When a team is five people, architecture is a technical question. When it is twenty, it is mostly an organizational one, and the codebase will end up shaped like the org chart whether you plan for it or not. That last part is Conway’s law, and on a growing iOS team it stops being a fun aphorism and starts being the thing that decides whether your release train runs on time.

The interesting question is not “what pattern should we use.” MVVM or TCA barely matters at this scale. The question is: where do you draw the lines so that twenty people can change the app at once without constantly breaking each other?

The failure mode you are designing against#

A team of five shares context in their heads. Everyone roughly knows how everything works, so a loose codebase is fine. The pain shows up around ten to fifteen people, and it always looks the same:

  • Merge conflicts in a handful of central files that everyone has to touch (the app delegate, the router, the giant Constants, the dependency container).
  • A change in one team’s feature silently breaks another team’s feature, because the boundary between them was a gentleman’s agreement, not a compiler rule.
  • Onboarding takes weeks because there is no boundary a new engineer can learn in isolation. To touch anything they have to understand everything.
  • Nobody owns the shared code, so it rots, and every team works around it instead of fixing it.

None of these are solved by a better pattern inside a screen. They are solved by boundaries that map to teams.

Boundaries as contracts between teams#

The core move is to make each team’s surface area an explicit, compiler-enforced contract. A feature module exposes a small public API and hides everything else. Another team consumes that API and physically cannot reach into the internals, because internal does not cross a module boundary.

This is the same modularization you would do for build times, but the reason here is social. The boundary is a promise: “this is what we support, the rest can change without warning.” When the Feed team can only see Profile’s public surface, the Profile team is free to refactor everything behind it without a cross-team meeting. That freedom is the entire point.

Two practices make this hold up:

Depend on interfaces, not implementations. If the Feed team imports ProfileImplementation, you have recreated the tangle with extra steps. Have features depend on small protocol-only modules and wire the concrete types together at the app’s composition root. Now teams depend on contracts, not on each other’s code, and you can even swap a real implementation for a stub to build and test a feature without the rest of the app.

Make the boundary the review boundary. Code ownership (a CODEOWNERS file, or the equivalent) should follow module lines, so a change to a module requires that module’s owners to approve. The contract is only real if changing it has a gatekeeper.

The shared-code problem, which is really an ownership problem#

Every growing team grows a shared module, and every shared module decays, for one reason: it is owned by everyone, which means no one. The fix is not technical. Give shared modules an explicit owner, the same as any feature, and hold a real bar for what is allowed in. “Three teams need it” is a weak reason to add to shared code; it is often better duplicated than coupled, because a shared dependency couples the release cadence of everyone who uses it. We will not relitigate the whole shared-module trap here, but the short version is: treat the addition of shared code as a cost, not a convenience.

Do not over-correct into ceremony#

The opposite failure is real too. A five-person team that adopts twelve modules, protocol indirection everywhere, and a strict layering doctrine has paid the twenty-person tax without having twenty people. Indirection has a cost: more files to open, more hops to trace, more ceremony per change. On a small team that moves fast on shared context, that ceremony is pure drag.

The honest path is incremental. Draw a boundary when a real seam appears, which is usually when two teams start colliding in the same code, or when one area of the app changes on a completely different rhythm from the rest. Let the org chart and the conflict history tell you where the lines go. They are more reliable than any upfront diagram, because they reflect how the software actually changes, which is the only thing architecture at this scale is trying to manage.

The summary a staff engineer would give: at twenty people you are not really designing an app, you are designing the interfaces between the teams that build it. Get those right, enforce them with the compiler and the review process, give every shared thing an owner, and the pattern inside each screen can be whatever that team likes.
