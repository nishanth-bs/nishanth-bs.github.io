Monolith vs Modular iOS: What Modularization Actually Costs

April 8, 2025 · 6 min · Beyond Swift
📊 ~... unique reads
Table of Contents

  • What it actually costs
  • Tooling, briefly

“Should we modularize the app?” gets argued like a values question, monolith for the scrappy, modules for the grown-ups. It is not a values question. Modularization buys specific things and costs specific things, both measurable, and the teams that get burned are the ones that paid the cost without checking whether they needed what it bought.

The usual pros-and-cons list (“easier to scale”, “more complex setup”) is too vague to decide with. Price it out instead.

What you are actually buying#

There are three real wins, and “scalability” is not one of them. These are.

Faster incremental builds. This is the one people feel daily. In a single target, the compiler’s incremental story is limited and a change in one corner can trigger a lot of recompilation. With clean module boundaries, touching a feature module rebuilds that module and its dependents, not the world. On a large app this is the difference between a 20-second and a 4-minute edit-build-run loop, which compounds across a team all day.

Enforced boundaries. In one target, internal is the whole app, so anything can reach into anything. Module boundaries make public a deliberate act. Code that is not exported cannot be imported, so accidental coupling stops compiling instead of quietly accumulating. This is the benefit that actually survives contact with a deadline, because the compiler enforces it and a tired engineer cannot route around it.

Parallel work and ownership. Separate modules let teams own and change code without colliding in the same files, and let you test a feature in isolation without booting the whole app.

Notice none of these require splitting into separate repositories. A modular monolith, many modules in one repo, gets you all three. Multi-repo adds versioning and integration cost and is a separate, heavier decision.

What it actually costs#

Here is the part the tutorials skip, and it is mostly about linking.

Launch time, if you link dynamically. Every dynamic framework (.framework / dynamic library) is something dyld has to find, load, and fix up before main runs. Historically, apps that split into dozens of dynamic frameworks paid a visible pre-main launch penalty, and Apple spent more than one WWDC telling people to reduce their dynamic framework count. Modern dyld and chained fixups have softened this, but it is not zero, and launch time is a metric users feel and the App Store reports.

So the real lever is static vs dynamic linking.

  • Static linking folds the module’s code into the app binary at build time. No dyld cost at launch, which is what you usually want for app-only code. The price is a larger binary, longer link times, and if two modules statically link the same dependency you can get duplicate symbols.
  • Dynamic linking keeps the module as a separate loadable binary. You pay at launch, but the code can be shared with app extensions (which run as separate processes) instead of duplicated into each one.

In Swift Package Manager this is a per-product decision, and it is easy to miss because the default hides it:

// Package.swift: linkage is a product-level choice
.library(name: "Analytics", targets: ["Analytics"]),                 // automatic: resolves to static in the app build, no launch cost
.library(name: "SharedKit", type: .dynamic, targets: ["SharedKit"]), // dynamic: pay at launch, but a share/widget extension can load the same binary

Leave off type: and the linkage is automatic, which Xcode resolves to static when it builds the app. You only write type: .dynamic when a separate process (an extension) needs the same code and you would rather load it once than bake a copy into each binary. Static unless the code must be shared with an extension. Getting this backwards, dozens of dynamic frameworks for app-only code, is the most common self-inflicted modularization slowdown.

The fat-core trap. The other big cost is self-inflicted through bad boundaries. Teams create a Core or Shared module and everything depends on it. Now every feature module sits downstream of Core, so a one-line change in Core rebuilds every feature. You modularized and made incremental builds worse.

    subgraph "Fat core: edit Core, rebuild everything"
        F1[Feature A] --> C[Core]
        F2[Feature B] --> C
        F3[Feature C] --> C
    end

The fix is to depend on interfaces, not implementations. Put protocols in tiny interface-only modules that almost never change, and let features depend on those. The heavy implementation modules sit at the leaves where nobody imports them, so changing an implementation does not cascade.

graph TD
    F1[Feature A] --> IAuth[AuthInterface]
    F2[Feature B] --> IAuth
    AuthImpl[AuthImplementation] --> IAuth
    App[App target] --> AuthImpl

The graph lives in the target dependencies. Read this Package.swift and answer one question before moving on: edit AuthImplementation, and which targets have to rebuild?

// Package.swift: features see the protocol, never the implementation
.target(name: "AuthInterface"),                                     // protocols only, changes rarely
.target(name: "AuthImplementation", dependencies: ["AuthInterface"]),
.target(name: "FeatureA", dependencies: ["AuthInterface"]),         // note: not AuthImplementation
.target(name: "FeatureB", dependencies: ["AuthInterface"]),
// only the app target depends on AuthImplementation, wiring it in at the composition root

Two: AuthImplementation itself, and the app target that wires it in. Nothing else. Feature A and Feature B depend on AuthInterface, a protocol module of a few lines that almost never changes, so they never import the implementation and never rebuild when it changes. That is the whole trick. This pattern, sometimes called the interface or contract module, is what separates a modularization that speeds builds from one that slows them, and it is the same discipline we walk through in designing feature modules and shared modules.

Tooling, briefly#

Swift Package Manager is the default now and the right starting point. It rejects circular target dependencies, so the moment FeatureA reaches back into something that already depends on it, the package fails to resolve with a cyclic-dependency error that names the chain (FeatureA -> ... -> FeatureA), and you untangle it that day instead of discovering it a year in. It integrates with Xcode and makes static-vs-dynamic an explicit choice. Framework targets in the Xcode project still work and give finer control over build settings. CocoaPods is legacy for new modular work. The choice matters less than the boundary discipline; a clean SPM graph with a fat core is still slow.

When a monolith is the right answer#

Premature modularization is as real as premature optimization, and worse to undo, because module boundaries calcify into API contracts that are painful to move later. A boundary drawn around the wrong abstraction is harder to fix than no boundary at all.

Stay a monolith when:

  • The app and team are small and the build is fast. You have nothing to buy yet.
  • The product is still finding its shape. You do not yet know where the real seams are, and guessing wrong locks in a bad split.

Modularization is a refactor you can do later, once the seams are obvious from how the code actually changes. The order that works is: build it, watch where the pain and the team boundaries land, then draw module lines along those, interfaces first, static by default, and never let everything pile into Core.
